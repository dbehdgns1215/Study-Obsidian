# 요구사항 수집

- 구축하고자 하는 시스템을 위한 요구사항에 관련된 다양한 자료를 수집
	- 비즈니스 문서: 회사의 비즈니스 프로세스, 정책, 규정 등을 설명하는 문서
	- 기존 시스템 문서: 현재 사용 중인 시스템의 문서, 데이터베이스 스키마, 사용자 매뉴얼 등
- 시스템
	- 기존 시스템: 현재 사용 중인 시스템의 데이터 흐름, 데이터 구조, 인터페이스 등을 분석
	- 경쟁사 시스템: 경쟁사의 시스템을 분석하여 유사한 요구사항을 도출
- 워크샵 및 인터뷰
	- 워크샵: 관련자들과의; 워크샵을 통해 도출
	- 인터뷰: 개별 인터뷰를 통해 도출
- 설문조사
	- 설문지: 대규모 사용자 그룹을 대상으로 설문조사를 실시하여 요구사항 수집
- 프로토타이핑
	- 프로토타입: 초기 프로토타입을 만들어서 사용자 피드백을 통해 요구사항 수집

# 요구사항 분석

- 수집한 정보를 체계적으로 정리하고 분석하여 개발할 데이터베이스의 용도를 파악
- 데이터베이스가 저장하고 관리해야 할 데이터의 구조, 관계, 제약 등을 명확히 정의하기 위해 요구사항을 분석하고 정리
- 비즈니스 규칙 도출 및 분석
- 데이터 흐름 및 업무 프로세스 분석
- 데이터베이스의 설계의 기초를 마련하는 중요한 단계
- 산출물
	- 요구 사항 명세서
	- 도메인 용어 사전
		- 시스템에서 사용되는 주요 용어와 개념을 정의하고 설명하는 문서
		- db 설계, 개발 과정에서 모든 이해관계자가 동일한 용어와 개념을 공유
		- 도메인 사전은 데이터가 의미 관계, 제약 조건 등을 명확히 정의
		- 모델링의 일관성을 유지하고 의사소통을 원할하게 함

# 개념적 데이터 모델링
- 업무 프로세스, 요구사항 분석을 통하여 정리된 자료를 다른 사람들이 이해하기 쉬운 형태로 표현
- 비즈니스 요구사항을 반영하여 개체(엔티티), 속성, 관계를 정의
- 언어로 표현한 것은 한눈에 파악하기 어렵고 관계 파악도 쉽지 않음
- 개체-관계 모델 가장 많이 사용됨
	- 개체(엔티티) 추출
	- 속성 추출
	- 관계 추론
- 산출물
	- 개념 ERD


## 개체(ENTITY)
- 시스탬에서 지속적으로 저장하고 관리하는 물리적, 개념적 대상
- 영속적이며 식별 가능한 데이터 요소를 걷어
- 일반적으로 분석한 정보를 토대로 명사형을 추출하는 방법으로 개체 식별 처리
- 현업에서 자주 사용하며 누구나 이해하기 쉬운 단어를 사용하되 중복되지 않도록 할 것

![[Pasted image 20251103145227.png]]

## 개체 식별
1. 명사로 된 단어 찾기
	- 개체와 속성의 후보
2. 비즈니스 분석 범위 내의 명사만 찾기
3. 찾은 명사 중 같은 의미로 사용되면서 다르게 표현되는 단어를 버릴 것
4. 여러 개의 속성으로 구성될 수 있는지 체크
5. 집합을 표현하는 지 체크

## 속성(Attribute)
- 하나의 엔티티에 종속되는 명사적 단어
- 엔티티를 표현하는 특성, 상태
	- ex) 회원 번호, 이름, 연락처

- 유형
	- 기본 속성: 업무 분석에서 도출된 본래의 속성
	- 설계 속성: 설계 과정에서 발생하는 인위적으로 추가하거나 변형한 속성
	- 파생 속성: 다른 속성에서 파생되어 계산된 속성

- 속성 추출
	- 분석 과정에서 추출된 명사 중 여러 개의 구성 요소를 갖지 않는 명사들

## 키(Key) 속성 추출
- 하나의 엔티티를 구성하는 속성 중 엔티티를 유일하게 식별하는 하나 이상의 속성 조합
- 모든 엔티티는 다른 엔티티와 구분이 가능한 단 하나의 식별자를 가져야 함
- 키 유형
	- 슈퍼키 (Super Key): 레코드를 유일하게 식별할 수 있는 모든 속성들의 가능한 조합 집합
	- 후보키 (Candidate Key): 슈퍼키 중 최소성을 만족하는 키
		- 식별하기 위한 최소한의 속성으로만 구성
		- 여러 개의 후보키 존재 가능
	- 기본키 (Primary Key): 후보키 중 가장 적합한 하나를 선택한 키
	- 대체키 (Alternate Key): 후보키 중 기본키가 아닌 것들
	- 인조키 (Artificial Key): 슈퍼키가 없을 때 인공적으로 만든 키

## 관계 차수(Cardinality) 정의
- 관계의 유형
	- 1 : 1 -> 한 엔티티의 한 개의 레코드가 다른 엔티티의 한 개의 레코드와 연결
	- 1 : N -> 한 엔티티의 한 개의 레코드가 다른 엔티티의 여러 개의 레코드와 연결
	- N : M -> 한 엔티티의 여러 개의 레코드가 다른 엔티티의 여러 개의 레코드와 연결

## 기본키 정의
- 후보키 중 가장 적합한 하나를 선택한 키
- 업무 활용도가 높고 길이가 너무 길지 않은 것이 좋음

## N : M 관계 해소
- N : M 관계는 데이터 중복이 발생할 수 밖에 없음
- 관계를 릴레이션으로 도출해서 1 : N의 관계로 풀어냄
- 관계 릴레이션의 기본키는 두 릴레이션의 기본키를 조합해 복합키 형태로 구성 또는 인공키 생성
- 관계 릴레이션에 관계 관련된 추가 속성도 정의 가능
- 두 릴레이션의 기본키가 관계 릴레이션의 외래키로 표현됨

![[Pasted image 20251103153528.png]]

## 외래키 정의
- 관계를 외래키로 표현
- 관계 차수에 따른 부모, 자식 릴레이션 확인 후 자식 릴레이션 쪽에 외래키 추가


## 정규화
- 데이터베이스에서 중복을 최소화하고 데이터 무결성 유지를 위해 새로운 엔티티를 도출하는 과정.
- 속성 간에 존재하는 함수적 종속성을 기반으로 유연한 구조로 정제하는 과정
- 제 1 정규화 ~ 제 5 정규화에 이르는 단계가 있지만 보통 제 3정규화까지면
- 장점
	- 데이터 중복 최소화로 인한 저장 공간 절약 및 성능 개선
	- 데이터 무결성 유지
	- 데이터 삽입/수정/삭제 이상 (Anomaly)
- 단점
	- 물리적 접근이 복잡해짐 -> 많은 조인 필요
	- 길이가 짧은 데이터 생김
