## 📝 Section 1: Docker Compose 기본 (1-5번)

### 문제 1

다음 중 Docker Compose 파일의 기본 이름은?

**선택지:**

- A) docker-compose.yaml
- B) compose.yml
- C) docker-compose.yml
- D) 모두 가능

**✅ 정답: D) 모두 가능**

**📖 해설:** Docker Compose는 다음 파일명을 모두 인식합니다:

- `docker-compose.yml` (가장 일반적)
- `docker-compose.yaml`
- `compose.yml` (Docker Compose V2부터)
- `compose.yaml`

**우선순위:** compose.yaml > compose.yml > docker-compose.yaml > docker-compose.yml

**실전 팁:** `docker-compose.yml`을 사용하는 것이 가장 보편적입니다.

### 문제 2

다음 설정의 의미는?

```yaml
restart: unless-stopped
```

**선택지:**

- A) 컨테이너가 중지되면 절대 재시작 안 함
- B) 수동으로 중지하지 않는 한 항상 재시작
- C) 에러 발생 시에만 재시작
- D) Docker 데몬 재시작 시에만 재시작

**✅ 정답: B) 수동으로 중지하지 않는 한 항상 재시작**

**📖 해설:**

- 컨테이너가 중지되면 자동 재시작
- **단, 사용자가 수동으로 중지(`docker stop`)한 경우는 재시작 안 함**
- Docker 데몬 재시작 후에도 자동 시작

**다른 옵션:**

- `no`: 재시작 안 함
- `always`: 무조건 재시작 (수동 중지해도)
- `on-failure`: 에러로 종료 시에만

**실전 팁:** 개발 환경에서는 `unless-stopped`가 가장 적합합니다.

### 문제 3

다음 중 올바른 `depends_on` 사용법은?

**선택지:**

- A) `depends_on: mysql`
- B) `depends_on: - mysql`
- C) `depends_on: mysql: condition: service_healthy`
- D) B와 C 모두 가능

**✅ 정답: D) B와 C 모두 가능**

**📖 해설:**

**방법 1: 단순 의존성**

```yaml
depends_on:
  - mysql
```

**방법 2: Health Check 조건 (권장!)**

```yaml
depends_on:
  mysql:
    condition: service_healthy
```

**차이점:**

- 방법 1: MySQL 컨테이너가 **시작**만 되면 Backend 시작
- 방법 2: MySQL이 **완전히 준비**(healthy)될 때까지 대기

**실전 팁:** DB는 시작 후 초기화 시간이 필요하므로 방법 2 권장!

### 문제 4

`docker-compose.yml`에서 `${MYSQL_PORT}` 변수는 어디서 가져오나?

**선택지:**

- A) 시스템 환경변수
- B) .env 파일
- C) docker-compose.yml 내부의 environment
- D) A와 B 모두

**✅ 정답: D) A와 B 모두**

**📖 해설:** Docker Compose는 환경변수를 다음 순서로 찾습니다:

1. 셸(Shell) 환경변수 (최우선)
2. `.env` 파일
3. `docker-compose.yml` 내부 `environment`

**우선순위:** Shell > .env > docker-compose.yml

```bash
# Shell 환경변수가 최우선
export MYSQL_PORT=3308
docker-compose up  # 3308 사용

# .env 파일이 두 번째
MYSQL_PORT=3307  # .env 파일
docker-compose up  # 3307 사용 (Shell에 없으면)
```

**실전 팁:** 팀 협업 시 `.env.example`을 제공하고 `.env`는 `.gitignore`에 추가!

### 문제 5

다음 명령어 중 컨테이너를 재빌드하는 것은?

**선택지:**

- A) `docker-compose up -d`
- B) `docker-compose up -d --build`
- C) `docker-compose build`
- D) B와 C 모두

**✅ 정답: D) B와 C 모두**

**📖 해설:**

```bash
# 방법 1: 빌드 + 실행
docker-compose up -d --build

# 방법 2: 빌드만
docker-compose build

# 차이점
up -d --build    # 이미지 빌드 → 컨테이너 시작
```

**실전 팁:**

- 코드 변경 후: `docker-compose up -d --build`
- Dockerfile 변경 후: `docker-compose build --no-cache` (캐시 무시)

## 📦 Section 2: Volume 관리 (6-10번)

### 문제 6

Named Volume과 Bind Mount의 차이는?

```yaml
# Case A
volumes:
  - mysql-data:/var/lib/mysql

# Case B
volumes:
  - ./backend:/app
```

**선택지:**

- A) A는 Named Volume, B는 Bind Mount
- B) A는 Docker가 관리, B는 호스트 경로 직접 마운트
- C) A는 영구 저장, B는 개발 시 핫 리로드용
- D) 모두 맞음

**✅ 정답: D) 모두 맞음**

**📖 해설:**

**Named Volume (`mysql-data:/var/lib/mysql`)**

```yaml
volumes:
  mysql-data:  # Docker가 관리
    driver: local
```

- Docker가 저장 위치 관리 (`/var/lib/docker/volumes/`)
- 영구 저장용
- 백업/복원 용이
- 플랫폼 독립적

**Bind Mount (`./backend:/app`)**

```yaml
volumes:
  - ./backend:/app  # 호스트 경로 직접 마운트
```

- 호스트 파일 시스템 직접 연결
- 실시간 코드 변경 반영 (핫 리로드)
- 개발 환경에 적합
- 플랫폼 의존적 (경로 차이)

**실전 팁:**

- DB 데이터: Named Volume
- 개발 중 소스코드: Bind Mount

### 문제 7

다음 중 MySQL 데이터를 영구 저장하는 올바른 방법은?

**선택지:**

- A) `volumes: - /var/lib/mysql`
- B) `volumes: - mysql-data:/var/lib/mysql` + `volumes: mysql-data:`
- C) `volumes: - ./mysql-data:/var/lib/mysql`
- D) B와 C 모두 가능

**✅ 정답: D) B와 C 모두 가능**

**📖 해설:**

**Named Volume (권장!)**

```yaml
mysql:
  volumes:
    - mysql-data:/var/lib/mysql

volumes:
  mysql-data:
    driver: local
```

- Docker가 관리
- `docker volume ls`로 확인 가능
- 플랫폼 독립적

**Bind Mount (로컬 백업용)**

```yaml
mysql:
  volumes:
    - ./mysql-data:/var/lib/mysql
```

- 호스트 폴더에 직접 저장
- 쉽게 확인/백업 가능
- 권한 문제 발생 가능 (특히 Linux)

**실전 팁:** Named Volume이 더 안전하고 이식성이 좋습니다!

### 문제 8

Maven 캐시를 Named Volume로 관리하는 이유는?

**선택지:**

- A) 빌드 속도 향상
- B) 의존성을 매번 다운로드하지 않기 위해
- C) 디스크 공간 절약
- D) A와 B 모두

**✅ 정답: D) A와 B 모두**

**📖 해설:**

**Maven 캐시 없이**

```dockerfile
RUN mvn dependency:go-offline  # 매번 3분 소요
```

**Maven 캐시 사용**

```yaml
backend:
  volumes:
    - maven-cache:/maven-cache

volumes:
  maven-cache:  # 한 번 다운로드한 의존성 저장
```

```dockerfile
RUN mvn dependency:go-offline -Dmaven.repo.local=/maven-cache
# 첫 빌드: 3분
# 이후 빌드: 5초! (캐시 재사용)
```

**실전 효과:**

- 첫 빌드: Spring Boot 의존성 다운로드 (~200MB)
- 소스만 변경: 의존성 재사용 (빌드 시간 90% 감소!)

### 문제 9

다음 볼륨 설정의 의미는?

```yaml
frontend:
  volumes:
    - ./frontend_v1:/app
    - /app/node_modules
```

**선택지:**

- A) frontend_v1 폴더를 마운트하되, node_modules는 컨테이너 것 사용
- B) 호스트와 컨테이너의 node_modules를 동기화
- C) node_modules를 호스트로 복사
- D) 잘못된 설정

**✅ 정답: A) frontend_v1 폴더를 마운트하되, node_modules는 컨테이너 것 사용**

**📖 해설:**

```yaml
volumes:
  - ./frontend_v1:/app           # 호스트 → 컨테이너 (덮어쓰기)
  - /app/node_modules            # 컨테이너 것 보호!
```

**동작 원리:**

1. `./frontend_v1:/app` → 호스트 폴더 전체를 `/app`에 마운트
2. `/app/node_modules` → 컨테이너의 `node_modules` 보호 (익명 볼륨)

**왜 필요한가?**

- 호스트에는 `node_modules` 없거나 다를 수 있음
- 컨테이너 안에서 `npm install`로 설치한 것 사용
- 플랫폼 차이 (Windows vs Linux) 방지

**실전 팁:** Frontend 핫 리로드 필수 설정!

### 문제 10

볼륨을 완전히 삭제하는 명령어는?

**선택지:**

- A) `docker-compose down`
- B) `docker-compose down -v`
- C) `docker volume prune`
- D) B와 C 모두

**✅ 정답: D) B와 C 모두**

**📖 해설:**

```bash
# 방법 1: 컨테이너와 볼륨 모두 삭제

# 방법 2: 사용하지 않는 볼륨만 삭제
```

```bash
docker-compose down     # 볼륨은 유지됨 (데이터 보존)
```

### 문제 11

다음 포트 매핑의 의미는?

```yaml
ports:
  - "3307:3306"
```

**선택지:**

- A) 호스트 3307 → 컨테이너 3306
- B) 컨테이너 3307 → 호스트 3306
- C) 호스트와 컨테이너 모두 3307
- D) 잘못된 설정

**✅ 정답: A) 호스트 3307 → 컨테이너 3306**

**📖 해설:**

```yaml
ports:
  - "3307:3306"
  # 형식: "호스트포트:컨테이너포트"
```

**포트 흐름:**

```
외부/호스트 → 3307 (호스트) → Docker 포트 포워딩 → 3306 (컨테이너)
```

**실전 예시:**

```bash
# 호스트에서 접근
mysql -h localhost -P 3307 -u root -p

# 컨테이너 내부에서
mysql -h localhost -P 3306 -u root -p
```

**왜 3307을 사용?**

- 호스트에 이미 MySQL이 설치되어 3306 사용 중일 수 있음
- 포트 충돌 방지!

### 문제 12

Spring Boot가 MySQL에 연결할 때 사용하는 URL은?

**선택지:**

- A) `jdbc:mysql://localhost:3307/mydb`
- B) `jdbc:mysql://mysql:3306/mydb`
- C) `jdbc:mysql://mysql-db:3306/mydb`
- D) B와 C 모두 가능

**✅ 정답: B) jdbc:mysql://mysql:3306/mydb**

**📖 해설:**

**Docker 네트워크 내부 통신:**

```yaml
# docker-compose.yml
services:
  mysql:        # ← 이 이름이 호스트명!
    container_name: mysql-db

  backend:
    environment:
      SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/mydb
      # mysql = 서비스 이름 (Docker DNS로 해석)
      # 3306 = 컨테이너 내부 포트
```

**틀린 답:**

- `localhost:3307` ❌ → 이건 호스트(외부)에서 접근할 때!
- `mysql-db:3306` ⚠️ → 가능하지만 서비스 이름 권장

**실전 팁:**

- 컨테이너 간: **서비스 이름** + **컨테이너 포트**
- 호스트에서: **localhost** + **호스트 포트**

### 문제 13

다음 중 컨테이너 간 통신에서 사용하는 것은?

**선택지:**

- A) 컨테이너 이름 (예: mysql)
- B) 서비스 이름 (예: mysql)
- C) localhost
- D) A와 B 모두 (같은 의미)

**✅ 정답: D) A와 B 모두 (같은 의미)**

**📖 해설:**

```yaml
services:
  mysql:                    # 서비스 이름
    container_name: mysql-db  # 컨테이너 이름

  backend:
    environment:
      # 둘 다 가능!
      DB_HOST: mysql        # 서비스 이름 (권장)
      DB_HOST: mysql-db     # 컨테이너 이름
```

**Docker DNS:**

- Docker가 자동으로 서비스 이름 → IP 변환
- 같은 네트워크 내에서만 작동

```bash
# backend 컨테이너 내부에서
ping mysql        # ✅ 작동
ping mysql-db     # ✅ 작동
ping localhost    # ❌ 자기 자신
```

**실전 팁:** 서비스 이름 사용이 더 명확하고 일관적!

### 문제 15

다음 설정에서 외부에서 접근 가능한 포트는?

```yaml
backend:
  ports:
    - "8080:8080"

frontend:
  ports:
    - "3000:3000"

mysql:
  ports:
    - "3307:3306"
```

**선택지:**

- A) 8080, 3000, 3307
- B) 8080, 3000, 3306
- C) 모두 접근 불가
- D) Docker 네트워크 내부에서만 접근 가능

**✅ 정답: A) 8080, 3000, 3307**

**📖 해설:**

```yaml
backend:
  ports:
    - "8080:8080"   # 호스트 8080 오픈 ✅

frontend:
  ports:
    - "3000:3000"   # 호스트 3000 오픈 ✅

mysql:
  ports:
    - "3307:3306"   # 호스트 3307 오픈 ✅
```

**외부에서 접근:**

```bash
curl http://localhost:8080    # Backend ✅
curl http://localhost:3000    # Frontend ✅
mysql -h localhost -P 3307    # MySQL ✅

# 컨테이너 포트로는 외부 접근 불가
curl http://localhost:3306    # ❌ 안 됨
```

**ports 설정 없으면:**

```yaml
mysql:
  # ports 없음!
```

- 컨테이너 간에만 통신 가능
- 외부(호스트)에서 접근 불가
- 보안상 더 안전!

**실전 팁:** 개발 시에만 ports 오픈, 프로덕션에서는 최소화!

### 문제 16

`docker-compose.yml`에서 환경변수를 주입하는 방법은?

```yaml
backend:
  environment:
    SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/${MYSQL_DATABASE}
```

**선택지:**

- A) `${MYSQL_DATABASE}`는 .env 파일에서 가져옴
- B) 컨테이너 내부의 환경변수로 설정됨
- C) backend/.env 파일은 사용 안 됨 (Docker 실행 시)
- D) 모두 맞음

**✅ 정답: D) 모두 맞음**

**📖 해설:**

**환경변수 전달 과정:**

```dotenv
# 1. .env 파일
MYSQL_DATABASE=yumcoach_db

# 2. docker-compose.yml (치환)
backend:
  environment:
    SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/${MYSQL_DATABASE}
    # → jdbc:mysql://mysql:3306/yumcoach_db

# 3. 컨테이너 내부
$ echo $SPRING_DATASOURCE_URL
jdbc:mysql://mysql:3306/yumcoach_db
```

**backend/.env는 사용 안 됨!**

```bash
# backend/.env (Docker 실행 시 무시됨!)
SPRING_DATASOURCE_URL=jdbc:mysql://localhost:3307/mydb

# Docker Compose가 주입한 환경변수가 우선!
```

**실전 팁:**

- Docker: `docker-compose.yml`의 `environment`
- 로컬 개발: `backend/.env` (IntelliJ)

### 문제 17

다음 중 Spring Boot가 사용하는 프로파일 설정은?


### 문제 18

Vite 개발 서버를 Docker에서 실행할 때 필수 설정은?

```dockerfile
ENV HOST=0.0.0.0
```

**선택지:**

- A) 127.0.0.1로 하면 외부 접근 불가
- B) 0.0.0.0으로 해야 호스트에서 접근 가능
- C) 컨테이너 내부 루프백 문제 해결
- D) 모두 맞음

**✅ 정답: D) 모두 맞음**

**📖 해설:**

```dockerfile
# ❌ 틀린 설정
ENV HOST=127.0.0.1
# 컨테이너 내부 루프백만 바인딩 → 외부 접근 불가!

# ✅ 올바른 설정
ENV HOST=0.0.0.0
# 모든 네트워크 인터페이스에 바인딩 → 외부 접근 가능!
```

**네트워크 바인딩:**

```
127.0.0.1 (localhost)
 └─ 컨테이너 내부에서만 접근 가능
 └─ 호스트에서 localhost:3000 → ❌ 연결 실패

0.0.0.0 (all interfaces)
 └─ 모든 IP에서 접근 가능
 └─ 호스트에서 localhost:3000 → ✅ 연결 성공
```

**Vite 설정:**

```javascript
// vite.config.js
export default {
  server: {
    host: '0.0.0.0',  // Docker에서 필수!
    port: 3000
  }
}
```

**실전 팁:** Docker에서 웹 서버 띄울 때는 항상 `0.0.0.0`!

### 문제 19

멀티스테이지 빌드의 장점은?

```dockerfile
FROM maven:3.9 AS build
...
FROM eclipse-temurin:17-jre-alpine
COPY --from=build /app/target/*.jar app.jar
```

**선택지:**

- A) 최종 이미지 크기 감소
- B) 빌드 도구가 최종 이미지에 포함 안 됨
- C) 보안 향상
- D) 모두 맞음

**✅ 정답: D) 모두 맞음**

**📖 해설:**

**단일 스테이지 (비추천):**

```dockerfile
FROM maven:3.9-eclipse-temurin-17
WORKDIR /app
COPY . .
RUN mvn package
CMD ["java", "-jar", "target/app.jar"]

# 최종 이미지 크기: 800MB+
# - JDK 포함
# - Maven 포함
# - 소스 코드 포함
```

**멀티 스테이지 (권장!):**

```dockerfile
# Stage 1: 빌드
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /app
COPY . .
RUN mvn package

# Stage 2: 런타임
FROM eclipse-temurin:17-jre-alpine
COPY --from=build /app/target/app.jar app.jar
CMD ["java", "-jar", "app.jar"]

# 최종 이미지 크기: 200MB
# - JRE만 포함 (JDK 제외)
# - Maven 제외
# - 소스 코드 제외
```

**장점:**

1. **크기 감소**: 800MB → 200MB (75% 감소!)
2. **보안 향상**: 빌드 도구, 소스 코드 노출 방지
3. **빠른 배포**: 작은 이미지 = 빠른 전송
4. **레이어 최적화**: 불필요한 레이어 제거

**실전 팁:** 프로덕션 환경에서는 멀티스테이지 필수!

### 문제 20

Health Check의 목적은?

```yaml
backend:
  healthcheck:
    test: ["CMD", "curl", "-f", "http://localhost:8080/actuator/health"]
  depends_on:
    mysql:
      condition: service_healthy
```

**선택지:**

- A) MySQL이 준비될 때까지 Backend 시작 대기
- B) 컨테이너 상태 모니터링
- C) 자동 재시작 판단 기준
- D) 모두 맞음

**✅ 정답: D) 모두 맞음**

**📖 해설:**

**Health Check 설정:**

```yaml
mysql:
  healthcheck:
    test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
    interval: 30s    # 30초마다 체크
    timeout: 10s     # 10초 안에 응답 없으면 실패
    retries: 5       # 5번 연속 실패하면 unhealthy

backend:
  depends_on:
    mysql:
      condition: service_healthy  # MySQL healthy 될 때까지 대기!
```

**동작 과정:**

```
1. MySQL 컨테이너 시작
2. Health Check 시작 (mysqladmin ping)
3. MySQL 초기화 중... (20초 소요)
4. Health Check 성공 → healthy 상태
5. Backend 시작 (MySQL 준비 완료!)
```

**Health Check 없으면:**

```
1. MySQL 시작
2. Backend 즉시 시작
3. Backend: "DB 연결 실패!" ❌
4. Backend 재시작 반복...
```

**컨테이너 상태:**

```bash
docker-compose ps

NAME       STATUS
mysql-db   Up 1 minute (healthy)      # ✅ 준비됨
backend    Up 30 seconds (health: starting)  # ⏳ 체크 중
```

**실전 팁:** DB, API 서버 등은 Health Check 필수!

## 🎓 핵심 요약

### Docker Compose 핵심

- **의존성 관리**: `depends_on`에 `condition: service_healthy` 사용
- **환경변수**: `.env` 파일 → `docker-compose.yml` → 컨테이너

### Volume 핵심

- **Named Volume**: Docker가 관리, 영구 저장 (DB 데이터)
- **Bind Mount**: 호스트 경로 직접 연결 (개발 핫 리로드)

### 네트워크 핵심

- **포트 매핑**: `"호스트포트:컨테이너포트"`
- **컨테이너 간 통신**: 서비스 이름 + 컨테이너 포트
- **브라우저 접근**: localhost + 호스트 포트

### 환경변수 핵심

- **Docker 실행**: `docker-compose.yml`의 `environment`
- **로컬 개발**: `backend/.env` (IDE)
- **우선순위**: Shell > .env > docker-compose.yml
