# 📘 Part 1 전체 시스템 아키텍처 개요

### 1. 환경별 구성 전략

우리 프로젝트는 **로컬 개발 환경**과 **실제 운영 서버 환경**을 분리하여 운영합니다.

|**구분**|**로컬 개발 (Local)**|**운영 서버 (Production/EC2)**|
|---|---|---|
|**목표**|빠른 개발 속도 및 디버깅 용이성|안정성, 보안, 자동화된 배포|
|**Spring Boot**|**IDE(IntelliJ)에서 직접 실행**|**Docker 컨테이너** 내부에서 실행|
|**Database**|**Docker** 컨테이너 (`localhost`)|**Docker** 컨테이너 (`hun-db-prod`)|
|**특징**|개발 편의를 위해 소스코드를 직접 수정|`Dockerfile`을 통해 빌드된 불변의 이미지 사용|

### 2. 협업 워크플로우

- **Code & Schema:** 소스코드(`.java`)와 DB 스키마 변경 사항(`.sql`)은 Git을 통해 공유합니다.
    
- **Data:** 로컬 DB 데이터는 각자의 컴퓨터(Docker Volume)에 저장되며, 팀원 간 공유되지 않습니다.
    
- **Deployment:** `Master` 브랜치에 코드가 푸시되면 **Jenkins**가 자동으로 감지하여 서버에 배포합니다.

# 📗 Part 2 로컬 개발 환경 구축 가이드 (팀원 필독)

모든 팀원은 개발 시작 전, 아래 절차에 따라 로컬 환경을 세팅해 주십시오.

프로젝트 최상단에 보안 파일(`.env`) 생성 및 `.gitignore` 설정이 필요합니다.

### 2. 로컬 DB 실행 (`docker-compose.yml`)

로컬에서는 데이터베이스만 Docker로 구동합니다.

**파일명:** `docker-compose.yml` (프로젝트 루트)

YAML

```
version: '3.8'

services:
  db:
    image: postgres:15-alpine
    container_name: local-postgres
    restart: always
    ports:
      - "5432:5432"
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
      TZ: Asia/Seoul
    volumes:
      # Named Volume 사용 (데이터 영구 보존)
      - postgres_data_local:/var/lib/postgresql/data

volumes:
  postgres_data_local:
```

### 3. 일일 개발 루틴 (Usage)

터미널에서 다음 명령어를 사용하여 개발 환경을 제어합니다.

1. **개발 시작 시 (DB 실행):**
    
    Bash
    
    ```
    docker-compose up -d
    ```
    
2. **서버 실행:** IntelliJ에서 `Application.java` 실행 (Run).
    
3. **개발 종료 시:**
    
    Bash
    
    ```
    docker-compose down
    ```

# 📙 Part 3 운영 배포 설정 (참고용)

이 섹션은 서버 배포를 위한 설정 파일에 대한 설명입니다. **팀원들은 이 파일을 직접 실행할 필요는 없으나, 구조를 이해하고 있어야 합니다.**

### 1. 멀티스테이징 Dockerfile

빌드 환경(Gradle)과 실행 환경(JRE)을 분리하여, 이미지 용량을 최소화하고 보안을 강화했습니다.

**파일명:** `Dockerfile`

Dockerfile

```
# [Stage 1] Build Stage: 소스코드 빌드 및 JAR 생성
FROM gradle:7.6-jdk17-alpine AS builder
WORKDIR /build
COPY . .
RUN gradle build -x test --parallel

# [Stage 2] Run Stage: 경량화된 실행 환경
FROM openjdk:17-jdk-slim
WORKDIR /app
# 빌드 스테이지에서 생성된 JAR 파일만 복사
COPY --from=builder /build/build/libs/*-SNAPSHOT.jar app.jar
ENV TZ=Asia/Seoul
ENTRYPOINT ["java", "-Dspring.profiles.active=prod", "-jar", "app.jar"]
```

### 2. 운영 환경 설정 (`application-prod.yml`)

로컬(`localhost`)과 달리, 운영 환경에서는 Docker 네트워크 내부 DNS를 사용합니다.

YAML

```
spring:
  config:
    activate:
      on-profile: prod
  datasource:
    # Docker Service Name을 호스트명으로 사용
    url: jdbc:postgresql://hun-db-prod:5432/hun_service_db
    username: ${POSTGRES_USER}
    password: ${POSTGRES_PASSWORD}
  jpa:
    hibernate:
      ddl-auto: validate # 운영 데이터 보호를 위해 validate 사용
    show-sql: false
```

# 📕 Part 4 CI/CD 자동화 프로세스 (Jenkins)

우리 팀은 **Jenkins**를 활용한 자동 배포 파이프라인을 구축했습니다. 배포 과정은 다음과 같이 진행됩니다.

### 1. 자동 배포 흐름

1. **Code Push:** 팀원이 코드를 작성하고 GitLab에 `push` 합니다.
    
2. **Build & Test:** Jenkins 서버가 변경 사항을 감지하여 코드를 빌드하고 테스트합니다.
    
3. **Dockerizing:** `Dockerfile`을 기반으로 새로운 Docker 이미지를 생성합니다.
    
4. **Deploy:** 운영 서버(EC2)의 기존 컨테이너를 중단하고, 새로운 버전으로 교체합니다. (`docker-compose down` -> `up`)
    

### 2. 팀원 주의사항

- **Jenkins 서버:** 별도의 EC2 인스턴스에서 24시간 가동됩니다. 팀원 개인이 설치할 필요는 없습니다.
    
- **환경 변수:** 운영 DB 비밀번호 등은 Jenkins 내부 Credentials로 안전하게 관리됩니다.
    
- **배포 확인:** 배포가 완료되면 공지된 서버 URL (`http://서버IP:8080`)에서 변경 사항을 확인할 수 있습니다.
