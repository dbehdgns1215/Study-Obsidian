# 📘 Part 1 전체 시스템 아키텍처 개요

### 1. 환경별 구성 전략

우리 프로젝트는 **로컬 개발 환경**과 **실제 운영 서버 환경**을 분리하여 운영합니다.

| **구분**          | **로컬 개발 (Local)**             | **운영 서버 (Production/EC2)**      |
| --------------- | ----------------------------- | ------------------------------- |
| **목표**          | 빠른 개발 속도 및 디버깅 용이성            | 안정성, 보안, 자동화된 배포                |
| **Spring Boot** | **IDE(IntelliJ)에서 직접 실행**     | **Docker 컨테이너** 내부에서 실행         |
| **Database**    | **Docker** 컨테이너 (`localhost`) | **Docker** 컨테이너 (`hun-db-prod`) |
| **특징**          | 개발 편의를 위해 소스코드를 직접 수정         | `Dockerfile`을 통해 빌드된 불변의 이미지 사용 |

### 2. 협업 워크플로우

- **Code & Schema:** 소스코드(`.java`)와 DB 스키마 변경 사항(`.sql`)은 Git을 통해 공유합니다.
    
- **Data:** 로컬 DB 데이터는 각자의 컴퓨터(Docker Volume)에 저장되며, 팀원 간 공유되지 않습니다.
    
- **Deployment:** `Master` 브랜치에 코드가 푸시되면 **Jenkins**가 자동으로 감지하여 서버에 배포합니다.

# 📙 Part 3 운영 배포 설정 (참고용)

이 섹션은 서버 배포를 위한 설정 파일에 대한 설명입니다. **팀원들은 이 파일을 직접 실행할 필요는 없으나, 구조를 이해하고 있어야 합니다.**

### 1. 멀티스테이징 Dockerfile

빌드 환경(Gradle)과 실행 환경(JRE)을 분리하여, 이미지 용량을 최소화하고 보안을 강화했습니다.

**파일명:** `Dockerfile`

Dockerfile

```
# [Stage 1] Build Stage: 소스코드 빌드 및 JAR 생성
FROM gradle:7.6-jdk17-alpine AS builder
WORKDIR /build
COPY . .
RUN gradle build -x test --parallel

# [Stage 2] Run Stage: 경량화된 실행 환경
FROM openjdk:17-jdk-slim
WORKDIR /app
# 빌드 스테이지에서 생성된 JAR 파일만 복사
COPY --from=builder /build/build/libs/*-SNAPSHOT.jar app.jar
ENV TZ=Asia/Seoul
ENTRYPOINT ["java", "-Dspring.profiles.active=prod", "-jar", "app.jar"]
```

### 2. 운영 환경 설정 (`application-prod.yml`)

로컬(`localhost`)과 달리, 운영 환경에서는 Docker 네트워크 내부 DNS를 사용합니다.

YAML

```
spring:
  config:
    activate:
      on-profile: prod
  datasource:
    # Docker Service Name을 호스트명으로 사용
    url: jdbc:postgresql://hun-db-prod:5432/hun_service_db
    username: ${POSTGRES_USER}
    password: ${POSTGRES_PASSWORD}
  jpa:
    hibernate:
      ddl-auto: validate # 운영 데이터 보호를 위해 validate 사용
    show-sql: false
```

# 📕 Part 4 CI/CD 자동화 프로세스 (Jenkins)

우리 팀은 **Jenkins**를 활용한 자동 배포 파이프라인을 구축했습니다. 배포 과정은 다음과 같이 진행됩니다.

### 1. 자동 배포 흐름

1. **Code Push:** 팀원이 코드를 작성하고 GitLab에 `push` 합니다.
    
2. **Build & Test:** Jenkins 서버가 변경 사항을 감지하여 코드를 빌드하고 테스트합니다.
    
3. **Dockerizing:** `Dockerfile`을 기반으로 새로운 Docker 이미지를 생성합니다.
    
4. **Deploy:** 운영 서버(EC2)의 기존 컨테이너를 중단하고, 새로운 버전으로 교체합니다. (`docker-compose down` -> `up`)
    

### 2. 팀원 주의사항

- **Jenkins 서버:** 별도의 EC2 인스턴스에서 24시간 가동됩니다. 팀원 개인이 설치할 필요는 없습니다.
    
- **환경 변수:** 운영 DB 비밀번호 등은 Jenkins 내부 Credentials로 안전하게 관리됩니다.
    
- **배포 확인:** 배포가 완료되면 공지된 서버 URL (`http://서버IP:8080`)에서 변경 사항을 확인할 수 있습니다.

## 1단계: 진입 장벽 Nginx (비동기 프로세스의 세계)

클라이언트가 요청을 보내면 가장 앞단에서 트래픽을 온몸으로 받아내는 구역입니다. Nginx는 스레드를 남발하지 않고 극소수의 '프로세스'로 수만 개의 연결을 통제합니다.

- **OS 커널과 TCP 소켓:** 클라이언트의 요청은 리눅스 커널의 네트워크 스택을 거쳐 80(HTTP) 또는 443(HTTPS) 포트를 두드립니다.
    
- **Master Process:** Nginx가 켜지면 가장 먼저 뜨는 프로세스입니다. 직접 일은 하지 않고 설정 파일을 읽어 **Worker Process**들을 낳습니다(`fork()`).
    
- **Worker Process (`worker_processes`):** 앞서 말씀드린 대로 보통 **서버의 CPU 코어 개수**만큼 생성됩니다. 스레드 전환 비용(Context Switching)을 아예 없애기 위해 각 CPU 코어에 하나씩 들러붙어 일합니다.
    
- **Event Loop와 `epoll` (`worker_connections`):** Nginx의 핵심입니다. 워커 프로세스 1개는 리눅스의 `epoll` 시스템 콜을 이용해 자신에게 할당된 수천 개의 커넥션(`worker_connections 4096`)을 한 번에 감시합니다. 데이터가 들어왔다는 '이벤트'가 발생할 때만 잽싸게 처리하고 톰캣으로 넘긴 뒤, 톰캣의 응답을 기다리지 않고(Non-blocking) 바로 다음 손님을 받습니다.
    

## 2단계: Nginx -> Tomcat (NIO와 스레드 풀의 바통 터치)

Nginx가 "이건 DB 조회가 필요한 동적 요청이군" 판단하고 톰캣으로 넘기면, 자바(Java)의 스레드 세계가 시작됩니다.

- **Acceptor Thread:** 톰캣의 문지기입니다. Nginx가 보낸 TCP 연결 요청(`accept`)만 빠르게 수락하고, 생성된 소켓 채널을 **Poller**에게 휙 던집니다.
    
- **Poller Thread:** 던져진 소켓들을 모아두고 계속 감시(Selector)합니다. 소켓에 HTTP Request Body 같은 실질적인 데이터가 다 도착하면, 그때 비로소 일을 처리할 수 있도록 포장해서 **Worker Thread Pool**에 넘깁니다.
    
- **Worker Thread (`threads.max`):** 우리가 흔히 말하는 "톰캣 스레드"입니다. `threads.max=300`으로 설정했다면 최대 300명의 직원이 대기 중인 겁니다. 큐에 일이 들어오면 쉬고 있던 스레드 하나가 깨어나 HTTP 메시지를 파싱하고 스프링이 읽을 수 있는 객체(`HttpServletRequest`)로 만듭니다.
    

## 3단계: Tomcat -> Spring Boot (애플리케이션 메모리 격리)

톰캣의 Worker Thread 1개가 요청을 짊어지고 JVM 위에 떠 있는 Spring 애플리케이션 안으로 들어옵니다.

- **DispatcherServlet 진입:** 스프링의 심장인 프론트 컨트롤러입니다. URL을 분석해 어느 컨트롤러의 어느 메서드로 가야 할지 길을 찾아줍니다.
    
- **`ThreadLocal` (데이터 격리):** 수백 개의 톰캣 스레드가 동시에 스프링 코드를 실행하더라도 데이터가 꼬이지 않는 이유입니다. `ThreadLocal`은 해당 스레드만 접근할 수 있는 전용 사물함입니다. 여기에 로그인한 유저의 세션 정보나 스프링 시큐리티의 인증 컨텍스트를 넣어두고 비즈니스 로직을 처리합니다.
    

## 4단계: 비즈니스 로직 -> HikariCP (병목의 시작점)

코드를 실행하다가 DB에서 회원의 정보를 가져오거나 수정해야 하는 순간이 옵니다. 여기서부터 **Blocking(대기)**이 발생합니다.

- **커넥션 대여 (`maximum-pool-size`):** DB와 TCP 연결을 맺는 건 시간이 아주 오래 걸리는 무거운 작업입니다. 그래서 HikariCP라는 풀(Pool)에 연결 통로를 미리 만들어 둡니다(예: 50개). 톰캣 스레드는 DB에 가기 전 무조건 여기서 커넥션 1개를 빌려야 합니다.
    
- **I/O Blocking:** 톰캣 스레드가 빌린 커넥션을 통해 쿼리를 DB로 쏩니다. **그리고 DB가 답을 줄 때까지 아무 일도 못 하고 그 자리에 얼어붙습니다(Blocking).** 만약 DB가 느려져서 스레드들이 300개 모두 멈춰버리면, 서버는 더 이상 새로운 요청을 받지 못하고 뻗어버립니다.
    

## 5단계: MySQL (영속성과 I/O 최적화)

쿼리가 데이터베이스 서버에 도착했습니다.

- **Foreground Thread (`max_connections`):** MySQL도 톰캣에서 날아온 커넥션 1개당 내부적으로 스레드 1개를 매칭시켜 쿼리를 실행합니다. 톰캣 여러 대가 동시에 붙는다면, `max_connections` 설정이 이 총합보다 커야 "Too many connections" 에러가 터지지 않습니다.
    
- **InnoDB 엔진과 트랜잭션:** 쿼리를 실행하여 메모리(Buffer Pool)의 데이터를 수정합니다.
    
- **Commit과 `trx_commit` 튜닝:** 작업이 끝난 데이터를 디스크(Redo Log)에 어떻게 쓸 것인지 결정합니다.
    
    - `1` (기본값): 커밋할 때마다 디스크에 씁니다. 안전하지만 매우 느립니다.
        
    - `2` (튜닝값): 커밋하면 디스크 대신 OS 캐시(메모리)까지만 쓰고 즉시 성공(OK)을 반환합니다. 실제 디스크 기록은 OS가 1초마다 백그라운드에서 알아서 처리합니다. **톰캣 스레드가 DB 응답을 기다리는 시간(Blocking 타임)을 획기적으로 줄여주는 필살기입니다.**
        

## 6단계: 응답과 자원 반납 (The Return)

DB에서 OK 사인이 떨어지면, 걸어왔던 길을 역순으로 광속 질주하며 자원을 정리합니다.

- **커넥션 반납:** 스프링은 쿼리 결과를 받자마자 HikariCP에 커넥션을 씻어서 반납합니다. (다른 스레드가 써야 하니까요)
    
- **메모리 청소:** 응답 HTML/JSON 데이터 생성이 끝나면, 워커 스레드는 `ThreadLocal` 사물함을 깨끗하게 비웁니다.
    
- **스레드 반납:** 톰캣 Worker Thread는 Nginx 쪽으로 응답 데이터를 쏴주고, 자신은 다시 스레드 풀로 돌아가 취침 모드에 들어갑니다.
    
- **Nginx의 쾌속 전송 (`keepalive`, `sendfile`, `nodelay`):**
    
    - 응답을 건네받은 Nginx 워커는 클라이언트에게 최종 데이터를 쏩니다.
        
    - **`keepalive_reqs`:** 연결된 TCP 파이프를 바로 끊지 않고, 다음 요청(이미지, JS 파일 등)을 위해 살려둡니다. 매번 3-way handshake를 하는 비용을 아낍니다.
        
    - **`tcp_nodelay`:** 네트워크 패킷을 모아서 보내지 않고 완성되는 족족 즉각 전송하여 Latency(지연 시간)를 최소화합니다.
        
    - **`sendfile`:** 정적 파일인 경우 커널 영역에서 다이렉트로 네트워크 카드로 데이터를 쏴버려 CPU 낭비를 막습니다.

|                                       | **`worker_connections`**                                  | 설정값    | 워커 프로세스 **1개가 동시에 처리할 수 있는 최대 커넥션 수**.                   | 서버의 **총 수용량** = `processes` × `connections`. 보통 수천~1만 단위로 넉넉히 설정.                              |
|                                       | **`epoll`**                                               | OS 기술  | Nginx 워커가 스레드 대기 없이 수만 개의 연결을 비동기로 감시하는 기술.              | 스레드 기반 서버(Apache 등) 대비 Nginx가 압도적으로 가벼운 이유.                                                    |
|                                       | **`keepalive_requests`**                                  | 설정값    | 한 번 맺은 TCP 연결을 끊지 않고 **최대 몇 개의 요청을 연달아 받을지** 설정.         | 브라우저가 화면을 그릴 때 필요한 여러 파일(JS, 이미지 등)을 빠르게 가져옴.                                                  |
|                                       | **`sendfile` / `tcp_nodelay`**                            | 설정값    | 정적 파일 서빙 최적화(디스크→네트워크 직행) 및 네트워크 패킷 지연 전송 방지.            | 응답 속도(Latency)를 극한으로 끌어올리는 가속 옵션. 보통 `on`으로 사용.                                                |
| **Tomcat**<br><br>  <br><br>(WAS)     | **`Acceptor` / `Poller`**                                 | 스레드    | 들어오는 연결을 받고(Acceptor), 진짜 데이터가 왔는지 감시(Poller)하는 문지기 스레드. | NIO(Non-blocking I/O) 모델의 핵심. 이들은 멈추지 않고 계속 일함.                                                |
|                                       | **`threads.max`**                                         | 설정값    | 실제 요청(비즈니스 로직)을 처리하기 위해 톰캣이 고용하는 **최대 워커 스레드 수**.        | 너무 크면 CPU가 스레드 관리하다 뻗고, 너무 작으면 대기열(Queue)이 꽉 차서 타임아웃 발생.                                       |
| **Spring**<br><br>  <br><br>(애플리케이션)  | **`ThreadLocal`**                                         | 메모리    | 각 톰캣 워커 스레드마다 할당되는 **격리된 개인 사물함**.                       | 요청이 동시에 쏟아져도 유저 인증 정보나 트랜잭션 데이터가 서로 섞이지 않게 보장.                                                 |
| **HikariCP**<br><br>  <br><br>(DB 연결) | **`maximum-pool-size`**                                   | 설정값    | WAS가 DB와 미리 맺어두고 재사용하는 **커넥션(통로)의 최대 개수**.               | **가장 흔한 병목 지점.** 스레드는 많은데 커넥션이 부족하면 여기서 전부 멈춤(Blocking).                                       |
| **MySQL**<br><br>  <br><br>(데이터베이스)   | **`max_connections`**                                     | 설정값    | DB 서버 전체가 외부로부터 허용하는 **최대 동시 접속 가능 통로 수**.               | `(모든 WAS의 pool-size 총합) + α` 보다 이 값이 커야 "Too many connections" 장애가 안 남.                        |
|                                       | **`Foreground Thread`**                                   | 스레드    | 연결된 커넥션 1개당 매칭되어 실제 SQL 쿼리를 실행하는 DB 전담 스레드.              | 커넥션이 유지되는 동안 1:1로 할당되어 대기/작업을 수행.                                                              |
|                                       | **`trx_commit`**<br><br>  <br><br>_(innodb_flush_log...)_ | 설정값    | 트랜잭션 Commit 시 데이터를 **디스크에 기록하는 시점/주기**를 결정.              | `1`=매번 디스크 기록(가장 안전/느림).<br><br>  <br><br>`2`=OS 메모리 기록 후 즉시 응답 반환(쓰기 성능 폭발적 증가, DB 대기시간 최소화). |
