# HTTP 톰캣 스레드

## HTTP Worker Threads
- 톰캣 서버가 HTTP 요청을 처리하기 위해 보유한 스레드
- 스레드풀 기본값은 200개
- 프론트에서 보내는 요청을 처리함
- `http-nio-exec-1` 이런 식으로 로그 찍힘

## Acceptor 스레드
- TCP 요청이 오면 문 열어주는 스레드

## Poller 스레드
- 홀 매니저(요청 다 왔는지 감시하다가 워커 스레드한테 배정)

---
## 애플리케이션 스레드 (Spring App Threads)

## main 스레드
- `java -jar` 실행할 때 main 메서드를 실행시키는 가장 첫 번째 스레드를 개념적으로 부르는 말

## 비동기/스케줄러 스레드 (App Threads)
- @Async 스레드
	- 백그라운드를 처리하는 스레드
		- `task-1`, `task-2` 로 불림
- @Scheduled 스레드
	- 배치 작업 수행하는 예약 스레드
		- 톰캣 스레드랑 별개의 풀임
			- `ThreadPoolTaskExecutor`을 사용함.

	- 기본 커넥션 풀 사이즈는 10, 시간은 30초
- Kafka/Redis 스레드
	- 메시지 큐나 캐시 쓸 때 사용되는 스레드

## JVM 시스템 스레드 (System Threads)
- GC 스레드 (Garbage Collector)
	- 안쓰는 객체 소멸시킴
- JIT 컴파일러 스레드
	- 자바 코드 기계어로 번역할 때 자주 쓰이는 코드 분석해서 최적화 시켜줌
- 기타
	- Signal Dispatcher
		- 외부 신호 감지
	- Reference Handler (청소부 조수)
	    - 수명이 다해서 메모리에서 날아갈 객체들의 참조 상태(Weak, Soft 등)를 깔끔하게 떼줌
	- inalizer 스레드 (유언 집행자)
	    - 객체가 죽기 직전에 마지막으로 실행해야 할 코드(`finalize()` 메서드)를 실행함
		    - (요즘은 성능 깎아먹는 주범이라 거의 안 쓰지만, JVM 안에는 여전히 살아있기는 함)
        
- **Attach Listener (내부 감사팀):**
    
    - 평소엔 자고 있다가, 형이 나중에 서버 장애 났을 때 터미널에서 `jstack`이나 `jcmd` 같은 명령어로 "야, 너네 지금 스레드 몇 개가 무슨 일해?" 하고 찌르면, 그걸 듣고 보고서(Thread Dump)를 쫙 뽑아주는 아주 고마운 놈이야.

### 1. HikariCP 커넥션 (Spring Boot 앱 계층)

- **정확한 의미:** 스프링 부트(Tomcat 스레드)가 DB와 통신하기 위해 미리 뚫어놓은 **'물리적인 TCP 네트워크 연결 통로'**의 집합이야.
- **상태 값:**
    - **Active:** 현재 톰캣 스레드가 쿼리를 들고 이 통로를 통해 DB랑 통신 중인 상태.
    - **Idle:** 통로는 열려있는데 아무도 안 쓰고 대기 중인 상태.
    - **Pending:** 통로(기본 10개)를 남들이 다 쓰고 있어서, 통로를 얻기 위해 톰캣 스레드가 **대기(Block) 중인 상태**.
- **한 줄 요약:** "우리 앱 서버가 DB로 가는 톨게이트를 몇 개나 열어두었고, 지금 톨게이트가 막혀서 차(요청)들이 밀리고 있는가?"

### 2. Threads_running (MySQL 프로세스 계층)

- **정확한 의미:** MySQL 서버 내부에서 **'실제로 CPU 자원을 할당받아 쿼리를 연산/실행 중인 OS 스레드의 개수'야.
- **상관관계 (HikariCP와의 연결):** 스프링 부트에서 HikariCP 통로 1개를 타고 쿼리가 날아오면, MySQL은 그걸 받아서 **자신의 워커 스레드 1개**를 할당해.
    - 즉, 통로만 연결되어 있고 쿼리가 안 날아오면 MySQL 스레드는 `Sleeping` 상태야. 반대로 쿼리가 날아와서 디스크를 뒤지거나 연산하는 그 순간에만 `Threads_running` 카운트가 올라가.
- **한 줄 요약:** "지금 DB 서버의 CPU가 몇 개의 쿼리를 동시에 멱살 잡고 처리하고 있는가?"

### 3. Row Lock (MySQL InnoDB 스토리지 엔진 계층)

- **정확한 의미:** InnoDB 엔진이 데이터 무결성을 지키기 위해, **특정 테이블의 행(Row)을 수정(Update/Insert/Delete)할 때 다른 스레드가 못 건드리게 잠가버리는 논리적 자원**이야.
- **특징:** 조회(Select)는 기본적으로 락을 안 걸어. 오직 쓰기 트랜잭션이 발생할 때만 해당 데이터에 '내 거!' 하고 자물쇠를 채워.
- **한 줄 요약:** "여러 요청이 동시에 같은 데이터를 수정하려고 할 때 발생하는 물리적인 데이터 쟁탈전."

### 4. InnoDB Buffer Pool Hit Ratio (DB 메모리 적중률)

- **어떤 개념이야?:** DB는 하드디스크(SSD)에서 데이터를 읽어오면 매우 느리니까, 자주 쓰는 데이터를 메모리(RAM)에 올려둬. 이 메모리 공간이 '버퍼 풀'이야. 적중률은 "내가 찾으려는 데이터가 하필 운 좋게 메모리에 딱 있었을 확률"을 말해. (보통 99% 유지해야 정상)
- **테스트 시나리오 연관성:** 시나리오 A(음악 탐색가)에서 랜덤 키워드로 막 검색을 때리면? DB가 "어? 처음 보는 데이터네?" 하면서 하드디스크를 박박 긁어와서 메모리에 쑤셔 넣어.
- **결과:** **적중률이 80% 밑으로 수직 낙하**하고, 디스크 I/O가 폭발하면서 쿼리 속도가 10배 이상 느려져. 👉 **이게 바로 무거운 검색(Read) 트래픽을 전담할 'DB Slave(Read Replica)'를 분리해야 하는 가장 완벽한 명분이야!**

### 5. Deadlock (데드락 - 교착 상태)

- **어떤 개념이야?:** 아까 말한 `Row Lock`의 흑화 버전이야. 스레드 A가 1번 곡을 잠그고 2번 곡을 잠그려는데, 스레드 B는 2번 곡을 잠그고 1번 곡을 잠그려고 해. 둘 다 영원히 서로의 락이 풀리기만 기다리는 상태야.
- **테스트 시나리오 연관성:** 시나리오 B(플리 생성/곡 추가 폭격)에서 트래픽이 몰리면, DB 내부에서 이 데드락이 펑펑 터지기 시작해. 데드락이 터지면 DB는 스스로 한 놈의 트랜잭션을 강제로 죽여버려(Rollback).
- **결과:** 유저 화면에 `500 Internal Server Error`가 그대로 꽂힘. 👉 **"동시에 몰리는 Write 요청 때문에 데드락이 잦아진다? ➔ Kafka 메시지 큐에 일렬로 세워서 한 놈씩(순차적으로) DB에 쓰게 만들어야겠다!"** 라는 카프카 도입 명분이 완성됨.

### 6. Tomcat Accept-Count & Max-Connections (OS 네트워크 큐)

- **어떤 개념이야?:** 스프링 부트(Tomcat)가 유저의 요청을 받아주는 앞단(프론트데스크) 지표야. `HikariCP Pending`이 톨게이트 병목이라면, 얘는 톨게이트 진입 전 **고속도로 톨게이트 대기줄(TCP 백로그 큐)**이야.
- **테스트 시나리오 연관성:** 톰캣 스레드 200개가 DB 커넥션을 못 구해서 전부 일시 정지(Block) 상태가 되면, 새로 들어오는 K6 가상 유저들의 요청은 이 `Accept-Count` 대기줄에 쌓여.
- **결과:** 이 대기줄마저 꽉 차버리면(기본 100개), 스프링 부트는 가차 없이 **`Connection Refused`**를 뱉어내며 유저의 접속 자체를 튕겨내버려. 앱 서버가 완전히 뻗었다는 최종 사망 선고지.

### 7. JVM GC Pause Time (가비지 컬렉션 정지 시간)

- **어떤 개념이야?:** 자바(Spring Boot)는 메모리(Heap)에 다 쓴 객체 쓰레기가 쌓이면 청소부(GC)를 불러. 문제는 이 청소부가 일할 때 **서버 전체가 잠깐 멈춰버려(Stop-the-World).**
- **테스트 시나리오 연관성:** 부하 테스트 1분 동안 톰캣이 수만 개의 DTO, Entity 객체를 찍어내잖아? 메모리가 미친 듯이 차오르고, GC가 쉴 새 없이 돌아가.
- **결과:** 평소엔 0.01초 멈추던 서버가, 과부하 상태에선 메모리 비우느라 **1~2초씩 멈춰버려(Pause).** DB가 아무리 빨라도 스프링 부트 자체가 멈춰있으니 지연 시간(Latency) 그래프가 미친 듯이 요동치게 돼.

### 💡 큰 그림: 이 지표들을 어떻게 엮을 것인가?

형이 포트폴리오 쓸 때 이 연관 관계를 쫙 나열하면 진짜 소름 돋는 글이 돼.

> "Write 트래픽 폭주로 인해 DB **Row Lock**이 걸리고, 이로 인해 **Threads_running**이 치솟습니다. 동시에 무거운 Read 트래픽이 **Buffer Pool**을 오염시키며 디스크 I/O를 유발합니다.
> 
> 
> DB가 느려지니 스프링 부트는 커넥션을 반납하지 못해 **HikariCP Pending**이 발생하고, 대기하는 톰캣 스레드들 때문에 객체가 메모리에 쌓여 **GC Pause**가 길어집니다. 결국 **Tomcat Accept-Count**까지 꽉 차며 서버가 다운되었습니다."
> 
> **"따라서 본 프로젝트에서는 Read 병목을 해소하기 위해 DB Slave를 추가하고, Write 병목(Lock)을 방지하기 위해 Kafka를 도입했습니다."**

### 💥 핵심: 1번 2번 3번의 "죽음의 도미노 (연관 관계)"

형이 설계한 부하 테스트(조회 폭격 + 쓰기 폭격)를 쏘면, 이 세 계층이 아래 순서대로 서로의 발목을 잡으면서 서버가 터져버려. 이 흐름을 포트폴리오에 쓰면 진짜 끝장나는 거야.

**[도미노 1단계: 락(Lock) 경합 발생 - DB 최하단]**

- VUs 20명이 동시에 "Plys 최고 인기 플레이리스트"에 곡을 추가(`INSERT/UPDATE`)하려고 해.
    
- InnoDB 엔진은 데이터가 꼬이는 걸 막기 위해 그 플레이리스트의 행(Row)에 **Row Lock**을 빡! 걸어버려.
    
- 1명이 락을 쥐고 있는 동안, 나머지 19명의 쓰기 요청은 락이 풀릴 때까지 대기(Lock Waits) 상태에 빠져.
    

**[도미노 2단계: Threads_running 폭증 - DB CPU/메모리 계층]**

- 나머지 19명의 쿼리를 담당하는 MySQL 스레드들은 락 대기 때문에 쿼리를 끝내지도 못하고, 그렇다고 연결을 끊지도 못하고 **DB 내부에서 정체**돼버려.
    
- 여기에 VUs 30명의 '무거운 검색(Read) 쿼리'까지 DB에 쏟아지니까, DB CPU가 일을 쳐내지 못하고 헉헉대면서 **`Threads_running` 수치가 수십 개로 치솟아.** (평소엔 1~3개임)
    

**[도미노 3단계: HikariCP Pending 폭발 - Spring Boot 앱 계층]**

- DB 스레드들이 정체(`Threads_running` 폭증)되니까, DB가 스프링 부트 쪽으로 쿼리 완료 응답(Result)을 안 보내줘.
    
- 쿼리가 안 끝나니까 스프링 부트의 톰캣 스레드들은 HikariCP 커넥션(`Active`)을 반납하지 않고 꽉 쥐고 있어.
    
- 통로 10개가 전부 막혔지? 이때 새로 들어오는 유저들의 요청은 톨게이트를 통과하지 못하고 **`HikariCP Pending` 상태로 무한 대기**하다가, 결국 30초 뒤에 `ConnectionTimeoutException`(HTTP 5xx 에러)을 뿜으며 앱 서버가 장렬하게 전사해.

# 프로메테우스/그라파나

## 메트릭(Metric) - "측정 항목"
- 측정 항목
	- 측정하려는 주제 그 자체
- `http_server_requests_seconds_count` (총 주문 건수)
- `hikaricp_connections_active` (현재 사용 중인 가스레인지 수)

## 인스턴스 (Instance) - "지점 1곳의 포스기"
- 프로메테우스가 데이터를 긁어오는 구체적인 타겟 주소 1개(`IP:Port`)
	- 도커 컨테이너를 3개 띄웠으면, 인스턴스도 3개가 됨 (예: `172.31.57.78:8081`)

## 잡 (Job) - "같은 역할을 하는 지점들의 묶음"
- 인스턴스들을 하나로 묶어주는 그룹 이름
	- 프로메테우스 설정 파일(`prometheus.yml`)에서 설정
- 예: 서버 3대가 다 백엔드 역할을 하면 이 3개의 인스턴스를 묶어서 `job="backend"`라고 부름
        

## 애플리케이션 (Application) - "브랜드명"
- 보통 스프링 부트 `application.yml`에 적어둔 프로젝트 이름
	- 예: `plys`
	- 모니터링 쿼리를 짤 때 "다른 잡다한 서버들 말고, 딱 `plys` 앱에서 나온 데이터만 줘!" 할 때 라벨(Label)로 씀

## 네임스페이스 (Namespace) - "거대한 상권 / 환경"
- 보통 쿠버네티스(k8s) 같은 데서 쓰는 가장 큰 울타리야. 망 자체를 논리적으로 쪼개버림
	- 예: `dev` (개발 서버 동네), `prod` (실제 운영 서버 동네).

## 메트릭 구조
```
http_server_requests_seconds_count{
	namespace="dev", # 가장 큰 울타리 치고
	application="plys", # 그 안에서 plys 프로젝트 찾고
	job="backend", # 그중 백엔드 역할하는 그룹 찾고
	instance="10...:8081" # 그 그룹의 1번 포스기 데이터만 줘!
}
```
