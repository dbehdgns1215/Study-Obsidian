
# 실무형 인프라 & CI/CD 아키텍처 총정리 노트

## 1. 부하 테스트 대상 API 선정 기준

모든 API를 테스트하는 건 리소스 낭비. 다음 4가지 기준에 해당하는 **핵심 API 20%**를 타겟으로 시나리오를 구성한다.

- **호출 빈도 (High Traffic):** 메인 홈 조회 등 트래픽이 가장 많은 Read API
    
- **비즈니스 중요도 (Business Critical):** 결제, 로그인 등 죽으면 서비스가 멈추는 핵심 API (DB 동시성/Lock 확인 필수)
    
- **리소스 병목 지점 (Resource Heavy):** 복잡한 Join, 대용량 파일 처리, 외부 API 호출 등 무거운 API
    
- **트래픽 스파이크 (Event Driven):** 이벤트, 푸시 알림 등 특정 시점에 확 몰리는 API
    

## 2. MSA/컨테이너 기반 레포지토리 분리 전략 (핵심)

애플리케이션 코드와 인프라 코드를 꽉 묶어두면 브랜치 전략(master/develop)이 꼬인다. 역할을 물리적으로 분리한다.

- **`plys-frontend`:** UI 코드 및 프론트 빌드 이미지 생성 역할 (`Dockerfile` 포함)
    
- **`plys-backend`:** Spring Boot 비즈니스 로직 및 백엔드 빌드 이미지 생성 역할 (`Dockerfile` 포함)
    
- **`plys-infra`:** 소스코드 0줄. 오직 **조립 설명서**(`docker-compose.yml`, `nginx.conf`, `prometheus.yml`)만 존재.
    

## 3. 운영/개발 서버 (EC2)의 작동 원리

**운영 EC2에는 백엔드/프론트엔드 소스코드가 존재하지 않는다.** 오직 `plys-infra` 레포지토리 하나만 클론(`git clone`)되어 있다.

- **경로 기준:** 모든 볼륨 마운트는 `docker-compose.yml`이 위치한 인프라 폴더 기준 **상대 경로(`./`)**를 사용한다.
    
- **코드 마운트 금지:** 백엔드(`.jar`)와 프론트엔드(`dist`) 코드는 도커 이미지 안에 완전히 **구워져서(Baked)** 오므로, 볼륨 마운트로 코드를 덮어씌우지 않는다.
    
- **데이터 보존:** DB나 모니터링 수집 데이터는 도커가 관리하는 **Named Volume**을 사용한다.
    
- **설정 파일 마운트:** Nginx나 Prometheus의 설정 파일(`.conf`, `.yml`)만 인프라 레포에서 파일 단위로 마운트한다.
    

## 4. 파이프라인(CI/CD) 흐름의 진실

무거운 빌드 작업은 서비스가 돌아가는 운영 서버에서 절대 하지 않는다.

1. **빌드 (CI Server):** GitLab Runner 등 별도의 봇 서버가 코드를 가져와 빌드하고 도커 이미지로 굽는다. (도커 레이어 캐싱으로 2회차부터 빠름)
    
2. **저장 (Registry):** 완성된 이미지를 Docker Hub에 푸시한다.
    
3. **배포 (CD Target):** 빌드 서버가 운영 EC2에 SSH로 원격 접속하여 `docker-compose pull` (새 이미지 다운) 후 `docker-compose up -d` (변경된 컨테이너만 재시작) 명령어를 날린다.
    

## 5. 파트별 협업 및 환경 분리

- **브랜치 매칭 국룰:**
    
    - `develop` 브랜치 ➡️ **Dev EC2 (개발 서버)** 자동 배포
        
    - `master` 브랜치 ➡️ **Prod EC2 (운영 서버)** 자동 배포
        
- **타 파트 연동 방법:** * 로컬에 남의 파트 코드를 클론받지 않는다!
    
    - 프론트엔드 로컬 환경에서는 API 호출 URL을 **개발 서버(`dev-api.도메인.com`)**로 돌려서 사용한다.
        
    - 완전 오프라인 로컬 환경이 필요하다면 인프라 레포의 `docker-compose.local.yml`을 이용해 최신 개발 이미지를 띄워 사용한다.
        

## 6. 콜드 스타트 (Day 0) 초기 세팅 4단계

자동화가 돌기 전, 텅 빈 EC2에서 딱 한 번 해줘야 하는 수작업.

1. **첫 이미지 굽기:** 각 레포에서 `v1.0` 도커 이미지를 수동으로 빌드해 Hub에 올린다.
    
2. **EC2 수동 세팅:** EC2에 접속해 `plys-infra` 레포를 클론하고, `.env` 파일을 직접 생성해 비밀번호를 입력한다.
    
3. **SSH 출입증 발급:** CI/CD 봇이 EC2에 접속할 수 있도록 SSH Key를 생성해 GitLab Variables에 등록한다.
    
4. **최초 실행:** EC2 내부에서 `docker-compose up -d`를 쳐서 첫 생명력을 불어넣는다.
    

## 7. 환경변수(.env) 관리의 정석

보안이 생명인 `.env` 파일은 절대 Git에 올리지 않는다.

- **백엔드 (Runtime Injection):** 도커 이미지 안에 비밀번호를 굽지 않는다! 무조건 깡통 이미지로 만들고, 운영 EC2에서 `docker-compose`가 켜지는 순간 EC2 로컬에 있는 `.env`를 주입받는다.
    
- **프론트엔드 (Build-time Injection):** 브라우저에서 돌아가는 정적 파일이므로, CI 파이프라인에서 빌드(`npm build`)할 때 변수를 코드 안에 구워 넣는다. (단, 비밀번호 등 민감 정보 포함 절대 금지)
    
- **업데이트 방법:** 개발 중 새 변수가 생기면, 배포 전에 운영 서버에 직접 접속해 `vi .env`로 추가해 주거나 파이프라인 변수로 자동 생성되게 스크립트를 짠다.

# 실무형 인프라 & CI/CD 아키텍처 심화 (환경 분리 & 파이프라인)

## 1. 개발(Dev) 서버 vs 스테이징(Staging) 서버의 진짜 차이

두 서버 모두 운영 배포 전 테스트를 위한 곳이지만, 역할과 스펙이 완전히 다릅니다.

|**구분**|**🛠️ 개발 (Dev) 서버**|**🎭 스테이징 (Staging) 서버**|
|---|---|---|
|**목적**|프론트-백 연동 및 새로운 기능 동작 확인 (모래놀이터)|배포 직전 최종 품질 검사(QA) 및 성능/부하 테스트|
|**안정성**|**불안정함** (하루에도 수십 번 배포되고 에러가 터짐)|**매우 안정적** (운영 서버와 동일한 퀄리티 보장)|
|**데이터**|**가짜 데이터 (Dummy)** (마음껏 지우고 깽판 쳐도 됨)|**운영 데이터 복제본** (실제 유저와 비슷한 데이터 볼륨)|
|**스펙**|**Low Spec** (가장 저렴한 인스턴스 사용)|**High Spec** (운영 서버와 100% 동일한 하드웨어)|

- **💡 현실적인 팁:** 스테이징 서버는 운영 서버와 100% 동일하게 구성해야 하므로 인프라 비용(AWS)이 정확히 2배로 듭니다. 스타트업이나 초기 프로젝트에서는 비용 문제로 스테이징을 생략하고 **Dev ➡️ Prod (2단계)** 구조로 가는 경우가 많습니다.
    

## 2. 개발(Dev) 서버의 4가지 핵심 역할

개발 서버는 절대 운영 Key를 넣지 않는, 철저한 **테스트 전용 샌드박스**입니다.

1. **프론트-백 최초 연동:** 로컬에서 발생하지 않던 CORS 에러, API 파라미터 불일치 등을 실제로 통신하며 맞춰가는 합숙소.
    
2. **외부 API '테스트 모드' 연동:** 카카오 로그인, 토스 간편결제 등의 '테스트용 Key'를 물려두고, 실제 돈이 빠져나가지 않는 안전한 환경에서 결제/가입 로직을 테스트.
    
3. **자유로운 QA 및 깽판 치기:** 데이터가 날아가도 상관없으므로, 기획자나 테스터가 온갖 예외 상황(이모티콘 도배, 비정상 접근 등)을 극한으로 테스트.
    
4. **팀원 간 작업물 공유:** 로컬 호스트가 아닌 공용 URL(`dev.도메인.com`)을 통해 누구나 현재까지의 개발 진행 상황을 눈으로 확인.
    

## 3. 환경변수(.env)를 철저히 분리해야 하는 3가지 이유

코드는 똑같지만, 서버가 켜질 때 주입되는 `.env` 이정표에 따라 서버의 운명이 결정됩니다.

- **① DB 연결 정보 분리:**
    
    - `Dev .env`: 마음껏 지워도 되는 테스트 DB 연결.
        
    - `Prod .env`: 철저히 백업되고 보호받는 실제 서비스 DB 연결. (운영 DB 비번이 개발 서버에 노출되는 대참사 방지)
        
- **② 외부 결제/API 키 분리:**
    
    - `Dev .env`: 결제 버튼을 눌러도 돈이 안 나가는 테스트 시크릿 키.
        
    - `Prod .env`: 누르면 실제 통장에서 돈이 출금되는 라이브 시크릿 키.
        
- **③ 로그 레벨 (Log Level) 조절:**
    
    - `Dev .env`: `DEBUG` (에러를 잡기 위해 쿼리문, 파라미터 등을 터미널에 미친 듯이 상세히 기록)
        
    - `Prod .env`: `ERROR` (서버 하드디스크 용량 폭발을 막기 위해, 진짜 심각한 에러가 났을 때만 기록)
        

> **✨ 도커의 위대함:** 빌드 서버(Jenkins)는 환경변수가 없는 **'깡통 이미지'**를 굽습니다. 이 똑같은 깡통이 개발 EC2에 떨어지면 Dev용 `.env`를 주워 먹고 개발 서버가 되고, 운영 EC2에 떨어지면 Prod용 `.env`를 주워 먹고 운영 서버로 변신합니다.

## 4. 파이프라인(Jenkins)과 인프라 레포 관리 전략

하나의 젠킨스와 똑같은 소스 코드로 두 개의 환경(Dev, Prod)을 완벽하게 자동 제어하는 방법입니다.

### 🔄 젠킨스의 브랜치(Branch) 기반 자동 라우팅

젠킨스는 어떤 브랜치에서 코드가 푸시되었는지 확인하고, 기계적으로 목적지와 명령어를 바꿉니다.

- **`develop` 브랜치 푸시 ➡️** `playlist-backend:dev` 이미지 생성 ➡️ **개발 EC2** 접속 ➡️ `docker-compose.dev.yml` 실행
    
- **`master` 브랜치 푸시 ➡️** `playlist-backend:latest` 이미지 생성 ➡️ **운영 EC2** 접속 ➡️ `docker-compose.prod.yml` 실행
    

### 🔐 환경변수(.env) 파일 관리법

`.env` 파일은 절대 Git 레포지토리에 올리지 않습니다. (gitignore 필수)

- **방법 1 (EC2 직접 관리):** 개발 EC2와 운영 EC2에 접속해 각자의 바닥(경로)에 `.env` 파일을 손으로 직접 만들어 둡니다. 도커가 켜질 때 자기 발밑에 있는 파일을 알아서 읽습니다.
    
- **방법 2 (Jenkins Credentials):** 젠킨스의 비밀번호 관리소에 Dev용/Prod용 환경변수 텍스트를 저장해 두고, 배포 스크립트가 실행될 때 봇이 각 EC2에 알맞은 `.env` 파일을 실시간으로 생성(덮어쓰기)합니다.
    

### 📁 최종 인프라 레포지토리(plys-infra) 구조 예시

하나의 인프라 레포지토리 안에서 환경별 설정 파일이 명확히 분리됩니다.

Plaintext

```
📦 plys-infra
 ┣ 📜 docker-compose.dev.yml   <-- 개발 서버용 조립 설명서 (가벼운 세팅)
 ┣ 📜 docker-compose.prod.yml  <-- 운영 서버용 조립 설명서 (무중단 배포, 리소스 제한 포함)
 ┣ 📂 nginx
 ┃ ┣ 📜 nginx.dev.conf         <-- 개발 서버용 라우팅 룰
 ┃ ┗ 📜 nginx.prod.conf        <-- 운영 서버용 라우팅 룰
 ┗ 📜 .gitignore               <-- .env 파일 등 보안 파일 제외
```
