# GIT

## COMMIT

[AngularJS](https://gist.github.com/stephenparish/9941e89d80e2bc58a153) 컨벤션 차용

```
<커밋 타입>: <제목>
<줄바꿈>
<바디>
<줄바꿈>
<푸터>

```

- `주제`는 필수
- `바디`, `푸터`는 선택 사항

### 커밋 타입 (Type)

|타입|설명|
|---|---|
|`feat`|새로운 기능 구현|
|`fix`|버그 수정|
|`style`|포맷팅, 줄바꿈, 세미콜론 등 **코드 동작에 영향을 주지 않는 수정**|
|`refactor`|기능은 유지한 채 코드 구조 변경|
|`docs`|문서 관련 변경|
|`test`|테스트 코드 추가 또는 수정|
|`chore`|빌드, 설정, 환경, 의존성 등 **코드 로직과 무관한 작업**|

### 제목

### 규칙

- 단답형 문체 사용
- 결과 중심 표현
- 한글 기준 50자 이내
- 마침표(`.`) 사용하지 않음

예시

```
feat: OAuth 로그인 기능 추가
fix: 로그인 시 토큰 검증 오류 수정
refactor: 로그인 검증 로직 분리
chore: Gradle 빌드 설정 정리

```

잘못된 예

```
feat: OAuth 로그인을 추가했습니다 -> 문장 X
fix: 로그인 버그를 수정함 -> 어떤 버그인지 추상적
refactor: 로그인 로직 개선 -> 무엇을 개선했는지 추상적

```

추상적인 부분은 개인에 따라 다소 다르게 느껴질 수 있으므로, `커밋 메시지 제목`에 `변경의 이유`를 설명할 수 있기만 하면 무관함.

### 본문

### 규칙

- 단답형 문체 사용
- 변화에 대한 동기 및 이전 행동과의 차이점 중심 표현
- 추가적으로 여러 변경 사항을 포함하고 싶은 경우는 또는 `들여쓴 -` 기호를 이용해 리스트로 표현

예시

```
feat: OAuth 로그인 기능 추가

기존 이메일 기반 로그인만 지원하던 구조에서 외부 인증 제공자를 통한 로그인 방식을 추가함

- Google OAuth API를 이용한 인증 플로우 구현
- 기존 로그인 방식과 병행 가능하도록 분기 처리
```

잘못된 예

```
fix: 로그인 시 오류 수정

버그가 있어서 고침
```

### 푸터

### 규칙

- 특정 이슈에 대한 해결 커밋인 경우 `Closes` 키워드와 함께 이슈 번호(`# 111`)를 명시
- 특정 이슈와 연관된 커밋인 경우 `See` 키워드와 함께 이슈 번호(`# 111`)를 명시
- 이슈를 완전히 해결하는 경우에만 `Closes`를 사용하며, 그 외의 경우에는 `see` 등 참조 형태로 연결한다.

### 이슈 관련

1. **이슈 먼저 생성**
    - `#111 로그인 토큰 검증 오류 발생`
2. 원인 분석 / 부분 작업 커밋
    - `fix: 로그인 토큰 검증 로직 로그 추가 See #111`
3. 최종 해결 커밋
    - `fix: 로그인 시 토큰 검증 오류 수정 Closes #111`

예시

```
fix: 로그인 시 토큰 검증 오류 수정

토큰 만료 여부를 검사하지 않아
만료된 토큰이 인증을 통과하는 문제가 발생함

- 만료 시간 검증 로직 추가
- 검증 실패 시 예외 처리 통합

Closes #111, #112
```

```
test: 로그인 토큰 검증 케이스 추가

토큰 만료 시 동작을 재현하기 위한 테스트를 추가함
문제 재현을 통해 원인 파악을 용이하게 함

See #111, #112
```

## Branch

### 기본 브랜치

### `main`

- 항상 **배포 가능한 상태**를 유지
- 반드시 PR을 통해서만 병합

### 작업 브랜치 규칙

### 브랜치 네이밍

`<타입>/<간단한-설명>`

|타입|용도|
|---|---|
|`feat`|기능 개발|
|`fix`|버그 수정|
|`refactor`|구조 개선|
|`chore`|설정, 환경 작업|
|`docs`|문서|
|`test`|테스트|

예시

- `feat/oauth-login`
- `fix/token-validation`
- `refactor/login-validation`
- `chore/gradle-config`

### 브랜치 생성 기준

- 하나의 브랜치는 **하나의 변경 의도**만을 가진다.
- 서로 다른 타입의 변경(`feat` + `refactor` 등)은 **반드시 브랜치를 분리**한다.

예시

- `refactor/login-structure`
- `feat/oauth-login`

잘못된 예

- `feat/login-and-refactor`

### 머지 전 체크 기준

머지는 항상 `Rebase And Merge` 규칙을 따른다.

### 규칙

- 커밋 컨벤션 최대한 준수
- 하나의 PR = 하나의 변경 의도

## 결론

- 커밋을 단순히 코드 변경 사항을 기록하는 것보다는 **의미 있는 변화 단위**로 기록하는 것이 핵심
- 파일의 수나 계층별로 커밋을 나누는 것이 아니고 **변경된 의도**를 기준으로, 일종의 **기능 단위**로 커밋을 나누는 것으로 한다.
- 머지의 경우, 최소 1인의 리뷰를 통해 이루어지게 한다.
