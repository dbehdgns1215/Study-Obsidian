
# 배경
운영 서버 / 개발 서버로 운용 중인 프로젝트.
개발 서버가 일종의 스테이징 서버의 역할을 하고 있음.

그런데 운영 서버와 개발 서버의 서버 스펙 및 구성이 달라서 절대 수치(TPS) 테스트 보다는 병목을 찾는 부하 테스트로 방향성을 설정함.

현재 개발 서버 및 운영 서버에서 수집 가능한 정보는
- Prometheus: 기본 메트릭
- Loki: 서버 로그 메트릭 
- Mysql Exporter: 쿼리 수행 시간, DB 오류, 연결 수 등 성능 메트릭
- Sentry: 실시간 런타임 에러 탐지 및 각종 요청 정보
- 
# 목적
**구조적 한계점(병목) 파악**
- 단순 트래픽 수용량(Capacity) 측정이 아닌, 부하 발생 시 시스템 내 가장 먼저 한계에 도달하는 컴포넌트(App Memory, Thread Pool, DB Connection 등) 식별.

**데이터 기반의 성능 튜닝**
- 수집된 메트릭과 로그를 교차 검증하여 인덱스 추가, 커넥션 풀 조정, 스로틀링 등 근거 있는 성능 개선 수행.

**운영 환경 리스크 최소화**
- 개발 서버에서 발견된 구조적 결함을 선제적으로 해결하여, 운영 서버 배포 시 발생할 수 있는 장애 사전 차단.

# 테스트 환경 및 시나리오
- **부하 발생 도구**: k6
- **테스트 방식**: 로컬 환경에서 개발 서버의 주요 API를 타겟으로 점진적 부하 인가 (Ramp-up 방식)
- **테스트 대상**: 주요 Read/Write API (DB I/O 발생 구간 및 외부 API 연동 구간 등 집중 타겟팅)

# 주요 관측 포인트 (Troubleshooting Flow)

부하 발생 시 4가지 모니터링 툴을 연계하여 병목 원인을 단계별로 추적함.

**1. 현상 감지 (Prometheus)**
- JVM Heap Memory 사용량 급증 여부
- Tomcat Worker Thread(`Busy`) 포화 상태 도달 여부
- HikariCP Connection Pool 고갈(`Pending` 증가) 및 HTTP 에러율(5xx, 4xx) 모니터링

**2. 원인 좁히기 - DB 레이어 검증 (Mysql Exporter)**
- `Slow Queries` 발생 여부 및 특정 쿼리의 처리 지연 확인
- `Threads_running` 수치 확인을 통한 DB CPU 병목 점검
- DB 내부 Table Lock 대기 상태 확인

**3. 에러 상세 분석 (Sentry & Loki)**
- `Loki`: 에러 발생 전후의 Nginx 접근 로그 및 Spring Boot 애플리케이션 로그의 전체 흐름(Context) 파악을 통한 인과관계 규명.
