# Research: 무중단 배포 (Zero-Downtime Blue/Green Deployment)

  
## 1. 현재 배포 구조 분석

### 1.1 현재 Jenkinsfile 배포 단계 (`Deploy to Prod` stage)

```groovy

sh "docker compose -f docker-compose.prod.yml pull backend-blue backend-green nginx"

sh "docker compose -f docker-compose.prod.yml up -d --force-recreate backend-blue backend-green nginx"

```

**문제점**: `--force-recreate`로 blue, green, nginx를 **동시에 내렸다 올림**.  
→ backend-blue 컨테이너가 재시작되는 수 초~수십 초 동안 **서비스 완전 중단(Downtime) 발생**.
→ Blue/Green 인프라는 이미 갖춰져 있지만, **Jenkins 스크립트가 이를 활용하지 않고 있음**.

  
---

### 1.2 현재 인프라 현황 (이미 갖춰진 것들)


| 구성 요소                     | 현재 상태                             | 비고               |
| ------------------------- | --------------------------------- | ---------------- |
| `backend-blue` (포트 8081)  | ✅ 운영 중 (restart: always)          | 현재 트래픽 수신 중      |
| `backend-green` (포트 8082) | ✅ 컨테이너 정의됨 (restart: on-failure)  | 대기 상태            |
| `nginx upstream`          | ✅ `playlist-backend-blue:8081` 고정 | green 주석 처리됨     |
| `nginx -s reload`         | ✅ Nginx가 지원하는 무중단 설정 리로드          | 기존 커넥션 유지됨       |
| `Spring Actuator /health` | ✅ Actuator 의존성 존재                 | 헬스체크 엔드포인트 활용 가능 |

**결론**: 인프라는 이미 Blue/Green을 지원하도록 설계되어 있다. **Jenkinsfile의 배포 스크립트만 교체**하면 된다.

  
---

### 1.3 nginx.conf 현재 upstream 구조

```nginx

upstream backend {

    server playlist-backend-blue:8081;

    # server playlist-backend-green:8082;  # Green 전환 시 주석 해제

}

```

현재는 주석을 수동으로 바꿔서 `nginx -s reload` 하는 **수동 전환** 구조.  
→ 이를 **자동화 스크립트**로 대체해야 함.

## 2. 무중단 Blue/Green 배포 원리

```

[배포 전]

트래픽 →  Nginx  →  backend-blue (v1, 운영 중)

                    backend-green (미실행 또는 구버전)

  

[배포 단계]

1. 새 이미지 Pull

2. backend-green (v2) 컨테이너 시작

3. green 헬스체크 통과 대기 (curl /actuator/health)

4. nginx upstream을 green으로 교체 → nginx -s reload

   (기존 blue 연결은 유지, 새 요청만 green으로)

5. backend-blue 컨테이너 중지

  

[배포 후]

트래픽 →  Nginx  →  backend-green (v2, 운영 중)

                    backend-blue (중지됨, 다음 배포 대기)

```

## 3. 핵심 구현 방법 - 배포 스크립트

Jenkinsfile의 `Deploy to Prod` stage를 하나의 쉘 스크립트로 대체.  

Jenkins가 EC2 동일 서버에서 실행 중이므로(`/workspace/S14P21B206/...` 경로 직접 접근 가능) **SSH 없이 직접 shell 실행** 가능.

### 스크립트 동작 흐름

```bash
# 1. 현재 활성 컬러 감지
#    nginx.conf를 읽어서 blue/green 중 어떤 게 현재 upstream인지 판단

# 2. 비활성 컬러(다음) 결정
#    active=blue → next=green (8082)
#    active=green → next=blue (8081)

# 3. 새 이미지 pull (next 컨테이너용)

# 4. next 컨테이너 --force-recreate로 시작

# 5. 헬스체크 루프
#    curl http://localhost:{next_port}/actuator/health
#    최대 60초 대기, 실패 시 rollback

# 6. nginx.conf upstream을 next로 교체
#    sed 명령어로 in-place 수정

# 7. docker exec playlist-nginx nginx -s reload
#    (Nginx 무중단 설정 반영 - 기존 커넥션 유지)

# 8. active 컨테이너(구버전) 중지
```

## 5. 주의사항 및 고려 포인트

### 5.1 프론트엔드(Nginx)는 무중단 처리가 필요한가?

**결론: 프론트는 Blue/Green 무중단 처리 불필요.**


Nginx 컨테이너는 프론트 정적 파일 서빙 + 리버스 프록시 두 역할을 동시에 함.  
프론트 코드가 변경될 때만 Nginx 컨테이너를 새 이미지로 재시작하면 되는데,  
Nginx 재시작 시간은 수 초 이내로 매우 짧아 실질적인 서비스 영향이 거의 없음.  

반면 Spring Boot 백엔드는 JVM 기동 시간이 수십 초이므로 무중단 처리가 반드시 필요.
→ **Nginx(프론트)는 기존처럼 `--force-recreate` 재시작 유지, 백엔드만 Blue/Green 전환 적용.**

  
### 5.2 Blue/Green 컨테이너의 버전 관계
Blue와 Green은 **항상 동일한 버전이 아님**. 교대로 최신/이전 버전이 됨.

```
[1차 배포]  Blue(v2, 운영 중) ← 트래픽     Green(v1, 중지)
[2차 배포]  Blue(v2, 중지)               Green(v3, 운영 중) ← 트래픽
[3차 배포]  Blue(v4, 운영 중) ← 트래픽     Green(v3, 중지)
```

**스크립트의 핵심 역할**: master 병합 시 Jenkins가 새 이미지를 Docker Hub에 올리면,  
스크립트가 현재 활성 컨테이너를 감지하고 **비활성 컨테이너에만** 새 이미지를 적용한 뒤 트래픽을 전환.  
→ 현재 Jenkinsfile처럼 blue를 항상 고정으로 재시작하는 방식 제거.


### 5.3 스테이징 테스트 활용 (Blue/Green 추가 장점)

비활성 컨테이너(예: Green)를 **스테이징 환경으로 활용** 가능.

```
현재 Blue(v2)가 운영 중

→ Green에만 v3 배포 (트래픽 전환 없이)

→ EC2에서 직접 Green 포트(8082)로 접근해서 테스트

→ 문제 없으면 Nginx upstream 전환 → Green이 운영

→ 문제 있으면 Green만 롤백 (Blue는 여전히 운영 중이므로 서비스 무중단)
```

이것이 Blue/Green의 핵심 장점 중 하나. **운영 중단 없이 신버전 검증 가능.**

### 5.4 nginx.conf upstream 전환 방식

`nginx.conf`는 nginx **Docker 이미지 안에 COPY**되어 있음 (`nginx/Dockerfile` 참고).  
→ 런타임에 컨테이너 내부의 `/etc/nginx/nginx.conf`를 `sed`로 수정 후 reload.  
→ **방식 A (docker exec + sed)** 채택: docker-compose.prod.yml 수정 없이 현 구조 최소 변경.  

단, nginx 컨테이너가 재시작되면 이미지 내 원본 conf로 돌아가므로,  

배포 스크립트 앞부분에서 현재 활성 컬러를 conf 파일 기준으로 감지하는 로직이 중요.

### 5.5 헬스체크 엔드포인트
`/actuator/health`는 현재 SecurityConfig에서 `permitAll()`로 열려있어 인증 없이 접근 가능. ✅  
단, Nginx에서 `actuator` location에 `allow 172.16.0.0/12; deny all;` 제한이 있음.  

→ 헬스체크 curl은 **Nginx를 거치지 않고** 컨테이너 포트(8081/8082)에 직접 접근해야 함.

### 5.6 첫 배포 시 green이 꺼져있는 상황
현재 green은 `restart: on-failure`로 평소에는 꺼져 있음.  
스크립트가 첫 실행 시에도 정상 동작하도록 처리 필요.


---

## 6. 결론

- **"Jenkinsfile에 무중단 배포 스크립트만 추가하면 된다"** → 사실상 맞음.
- 정확히는 Jenkinsfile + 별도 `infra/scripts/deploy.sh` 스크립트 파일 추가 조합.
- `docker-compose.prod.yml`은 **건드릴 필요 없음** (이미 준비됨).
- **프론트(Nginx)는 무중단 처리 불필요** - 재시작 시간이 매우 짧고 Blue/Green 구조 불필요.
- **백엔드만 Blue/Green 전환 자동화** - nginx upstream을 `sed`로 교체 후 `nginx -s reload`.
- 비활성 컨테이너를 스테이징 환경으로 활용 가능 (운영 영향 없이 신버전 검증).

## Step 1: `infra/scripts/deploy.sh` 신규 생성

Blue/Green 전환 로직을 담당하는 핵심 스크립트. Jenkins에서 호출됨.


**구현 내용:**
```

1-1. nginx 컨테이너 내부의 nginx.conf를 읽어 현재 활성 컬러 감지
     → "playlist-backend-blue" 문자열 있으면 active=blue, 없으면 active=green

1-2. next 컬러 및 포트 결정
     → active=blue  : next=green, next_port=8082, next_container=playlist-backend-green
     → active=green : next=blue,  next_port=8081, next_container=playlist-backend-blue


1-3. Docker Hub에서 최신 이미지 pull

1-4. next 컨테이너 --force-recreate 로 시작
     (docker compose -f docker-compose.prod.yml up -d --force-recreate {next})
 

1-5. 헬스체크 루프 (최대 60초, 3초 간격)
     → curl -sf http://localhost:{next_port}/actuator/health
     → 통과 시 다음 단계 진행
     → 타임아웃 시 next 컨테이너 중지 후 스크립트 exit 1 (롤백)

1-6. nginx.conf upstream 교체
     → docker exec playlist-nginx sed -i 명령으로
       "playlist-backend-{active}" → "playlist-backend-{next}" 치환

1-7. nginx 무중단 설정 리로드
     → docker exec playlist-nginx nginx -s reload


1-8. 구버전(active) 컨테이너 중지
     → docker compose -f docker-compose.prod.yml stop {active}
```

`Jenkinsfile`
```Jenkinsfile
pipeline {  
    agent any  
  
    environment {  
        // [수정 필요] 도커 허브 아이디  
        DOCKER_USERNAME = 'yudongni'  
        IMAGE_NAME = 'playlist-backend'  
        IMAGE_NAME_NGINX = 'playlist-nginx'  
  
        // 젠킨스에 등록해 둔 인증서(Credentials)의 ID        DOCKER_CREDS_ID = 'docker-hub-credentials'  
        // 프론트엔드 빌드 시 Vite 에서 사용할 백엔드 서비스 주소 (컨테이너 네트워크 기준)  
        // nginx.conf 의 upstream backend 를 통해 playlist-backend-* 로 라우팅되므로 http://backend 로 고정 사용  
        VITE_BACKEND_SERVICE = 'http://backend'  
    }  
  
    stages {  
        stage('Checkout') {  
            steps {  
                checkout scm  
            }  
        }  
  
  
        stage('Docker Build (Backend & Nginx)') {  
            steps {  
                // 1. Backend Image Build                dir('plys-backend') {  
                    sh "docker build -t ${DOCKER_USERNAME}/${IMAGE_NAME}:${BUILD_NUMBER} -t ${DOCKER_USERNAME}/${IMAGE_NAME}:latest ."  
                }  
                  
                // 2. Nginx (Frontend) Image Build                // 주의: context는 최상위 폴더(.)로 잡고 파일은 infra/nginx/Dockerfile을 사용  
                    sh "docker build --build-arg VITE_BACKEND_SERVICE=${VITE_BACKEND_SERVICE} -t ${DOCKER_USERNAME}/${IMAGE_NAME_NGINX}:${BUILD_NUMBER} -t ${DOCKER_USERNAME}/${IMAGE_NAME_NGINX}:latest -f plys-backend/infra/nginx/Dockerfile ."  
            }  
        }  
  
        stage('Docker Push') {  
            steps {  
                withCredentials([usernamePassword(credentialsId: "${DOCKER_CREDS_ID}", passwordVariable: 'DOCKER_PASS', usernameVariable: 'DOCKER_USER')]) {  
                    sh "echo \$DOCKER_PASS | docker login -u \$DOCKER_USER --password-stdin"  
  
                    // Push Backend                    sh "docker push ${DOCKER_USERNAME}/${IMAGE_NAME}:${BUILD_NUMBER}"  
                    sh "docker push ${DOCKER_USERNAME}/${IMAGE_NAME}:latest"  
  
                    // Push Nginx (Frontend)                    sh "docker push ${DOCKER_USERNAME}/${IMAGE_NAME_NGINX}:${BUILD_NUMBER}"  
                    sh "docker push ${DOCKER_USERNAME}/${IMAGE_NAME_NGINX}:latest"  
                }  
            }  
        }  
  
        stage('Deploy to Prod (Auto CD)') {  
            steps {  
                echo '=== 최신 이미지 운영 서버에 자동 배포(무중단 Blue/Green) 시작 ==='  
  
                dir('plys-backend/infra') {  
                    // 0. 호스트에서 볼륨 마운트된 진짜 .env 파일을 현재 젠킨스 작업 폴더로 복사  
                    // 이렇게 하면 yml 파일 안의 `env_file: - .env` 가 이 파일을 읽고 컨테이너 내부로 모든 변수를 밀어넣음!  
                    sh "cp /workspace/S14P21B206/plys-backend/infra/.env ./.env"  
  
                    // 1. 프론트 (Nginx) - 기존 방식 유지 (재시작 시간 짧아 다운타임 미미)  
                    sh "docker compose -f docker-compose.prod.yml pull nginx"  
                    sh "docker compose -f docker-compose.prod.yml up -d --force-recreate nginx"  
  
                    // 2. 백엔드 - Blue/Green 무중단 배포 (deploy.sh 위임)  
                    //    현재 활성 컬러 자동 감지 → 비활성 컨테이너에 배포 → 헬스체크 → nginx upstream 전환 → 구버전 중지  
                    sh "chmod +x scripts/deploy.sh"  
                    sh "bash scripts/deploy.sh"  
                }  
            }  
        }  
  
        // 찌꺼기 청소  
        stage('Cleanup Local Images') {  
            steps {  
                dir('plys-backend') {  
                    sh "docker rmi ${DOCKER_USERNAME}/${IMAGE_NAME}:${BUILD_NUMBER} || true"  
                    sh "docker rmi ${DOCKER_USERNAME}/${IMAGE_NAME}:latest || true"  
                    sh "docker logout"  
                }  
            }  
        }  
    }  
}
```


`deploy.sh`
```bash
#!/bin/bash
# =============================================================================
# Blue/Green 무중단 배포 스크립트
# - nginx.conf를 읽어 현재 활성 컬러(blue/green) 자동 감지
# - 비활성 컨테이너에 새 이미지 배포 후 nginx upstream 전환
# - 헬스체크 실패 시 롤백
#
# 실행 위치: infra/ 디렉터리 내부 (Jenkins Deploy to Prod stage에서 호출)
# 사전 조건: docker, docker compose, curl 설치 필요
#            nginx 컨테이너(playlist-nginx)가 실행 중이어야 함
# =============================================================================

set -e  # 에러 발생 시 즉시 중단

COMPOSE_FILE="docker-compose.prod.yml"
NGINX_CONTAINER="playlist-nginx"
HEALTH_CHECK_MAX=20   # 최대 대기 횟수 (20 * 3초 = 60초)
HEALTH_CHECK_INTERVAL=3

# =============================================================================
# Step 1. 현재 활성 컬러 감지
# nginx 컨테이너 내부의 nginx.conf에서 upstream 블록을 읽어 판단
# =============================================================================
echo ">>> [1/6] 현재 활성 컬러 감지 중..."

CURRENT_UPSTREAM=$(docker exec $NGINX_CONTAINER grep -o 'playlist-backend-[a-z]*' /etc/nginx/nginx.conf | head -1)

if echo "$CURRENT_UPSTREAM" | grep -q "blue"; then
    ACTIVE="blue"
    ACTIVE_PORT=8081
    NEXT="green"
    NEXT_PORT=8082
elif echo "$CURRENT_UPSTREAM" | grep -q "green"; then
    ACTIVE="green"
    ACTIVE_PORT=8082
    NEXT="blue"
    NEXT_PORT=8081
else
    echo "[ERROR] nginx.conf에서 upstream 컬러를 감지할 수 없습니다."
    echo "        감지된 값: $CURRENT_UPSTREAM"
    exit 1
fi

ACTIVE_CONTAINER="playlist-backend-${ACTIVE}"
NEXT_CONTAINER="playlist-backend-${NEXT}"

echo "    현재 활성: ${ACTIVE} (${ACTIVE_CONTAINER}:${ACTIVE_PORT})"
echo "    배포 대상: ${NEXT}  (${NEXT_CONTAINER}:${NEXT_PORT})"

# =============================================================================
# Step 2. 최신 이미지 Pull
# =============================================================================
echo ""
echo ">>> [2/6] 최신 이미지 Pull 중..."

docker compose -f $COMPOSE_FILE pull backend-${NEXT}

# =============================================================================
# Step 3. next 컨테이너 시작 (force-recreate)
# =============================================================================
echo ""
echo ">>> [3/6] ${NEXT_CONTAINER} 컨테이너 시작 중..."

docker compose -f $COMPOSE_FILE up -d --force-recreate backend-${NEXT}

# =============================================================================
# Step 4. 헬스체크 루프 (최대 60초 대기)
# Nginx를 거치지 않고 컨테이너 포트에 직접 접근
# =============================================================================
echo ""
echo ">>> [4/6] 헬스체크 대기 중... (최대 ${HEALTH_CHECK_MAX}회 * ${HEALTH_CHECK_INTERVAL}초)"

COUNT=0
while [ $COUNT -lt $HEALTH_CHECK_MAX ]; do
    # 백엔드 컨테이너는 호스트에 포트가 노출되지 않으므로
    # docker inspect로 컨테이너 내부 IP를 가져와서 호스트에서 직접 curl
    CONTAINER_IP=$(docker inspect -f '{{range.NetworkSettings.Networks}}{{.IPAddress}}{{end}}' ${NEXT_CONTAINER} 2>/dev/null)
    HTTP_STATUS=$(curl -s -o /dev/null -w "%{http_code}" --connect-timeout 3 "http://${CONTAINER_IP}:${NEXT_PORT}/actuator/health" 2>/dev/null || echo "000")

    if [ "$HTTP_STATUS" = "200" ]; then
        echo "    헬스체크 통과! (시도: $((COUNT + 1))회, IP: ${CONTAINER_IP})"
        break
    fi

    COUNT=$((COUNT + 1))
    echo "    대기 중... HTTP ${HTTP_STATUS} (${COUNT}/${HEALTH_CHECK_MAX}, IP: ${CONTAINER_IP})"

    if [ $COUNT -eq $HEALTH_CHECK_MAX ]; then
        echo ""
        echo "[ERROR] 헬스체크 타임아웃! ${NEXT_CONTAINER} 컨테이너를 중지하고 롤백합니다."
        docker compose -f $COMPOSE_FILE stop backend-${NEXT}
        exit 1
    fi

    sleep $HEALTH_CHECK_INTERVAL
done

# =============================================================================
# Step 5. nginx.conf upstream 교체
# 컨테이너 내부 파일을 sed로 in-place 수정
# =============================================================================
echo ""
echo ">>> [5/6] nginx upstream 전환: ${ACTIVE} → ${NEXT}"

docker exec $NGINX_CONTAINER sed -i \
    "s/server playlist-backend-${ACTIVE}:${ACTIVE_PORT}/server playlist-backend-${NEXT}:${NEXT_PORT}/g" \
    /etc/nginx/nginx.conf

# 전환 결과 확인용 출력
UPDATED_UPSTREAM=$(docker exec $NGINX_CONTAINER grep -o 'playlist-backend-[a-z]*:[0-9]*' /etc/nginx/nginx.conf | head -1)
echo "    nginx.conf upstream → ${UPDATED_UPSTREAM}"

# =============================================================================
# Step 6. nginx 무중단 설정 리로드
# 기존 커넥션은 유지되고, 새 요청부터 next 컨테이너로 라우팅됨
# =============================================================================
echo ""
echo ">>> [6/6] nginx 무중단 리로드 중..."

docker exec $NGINX_CONTAINER nginx -s reload

echo "    nginx reload 완료. 트래픽이 ${NEXT_CONTAINER}로 전환되었습니다."

# =============================================================================
# Step 7. 구버전(active) 컨테이너 중지
# =============================================================================
echo ""
echo ">>> 구버전 컨테이너 중지: ${ACTIVE_CONTAINER}"

docker compose -f $COMPOSE_FILE stop backend-${ACTIVE}

echo ""
echo "================================================================"
echo "  무중단 배포 완료!"
echo "  활성: ${NEXT_CONTAINER} (포트 ${NEXT_PORT})"
echo "  대기: ${ACTIVE_CONTAINER} (중지됨)"
echo "================================================================"

```



# 흐름
## 1. 무중단 배포 파이프라인 핵심 흐름

우리 프로젝트의 무중단 배포는 `deploy.sh` 스크립트를 통해 Nginx의 `upstream`을 동적으로 교체하는 방식으로 이루어집니다. 새 버전의 컨테이너를 띄우고 헬스체크가 통과되면 Nginx가 트래픽을 새 컨테이너로 부드럽게 넘겨줍니다.

### 전체 흐름 요약

1. **컨테이너 내부 파일 읽기:** Nginx 설정에서 현재 활성화된(Active) 컨테이너 컬러(Blue 또는 Green)를 확인합니다.
    
2. **변수 세팅:** 새롭게 배포할 대기(Next) 컬러와 포트를 지정합니다.
    
3. **신규 컨테이너 실행 및 헬스체크:** Next 컬러의 컨테이너를 띄우고 정상적으로 응답하는지 대기합니다.
    
4. **Upstream 교체:** Nginx 설정 파일 내의 라우팅 주소를 신규 컨테이너로 치환합니다.
    
5. **Nginx 리로드:** 기존 커넥션을 유지한 채 Nginx 설정만 다시 읽어 트래픽을 전환합니다.
    
6. **구버전 컨테이너 중지:** 이전 버전의 컨테이너를 내립니다.

## 2. 배포 스크립트(`deploy.sh`) 핵심 로직 분석

스크립트가 실제로 어떻게 Nginx를 제어하는지 핵심 명령어 2가지를 이해하는 것이 중요합니다.

### ① 활성 컬러 감지 (설정 파일 읽기)

현재 Nginx가 바라보고 있는 타겟이 Blue인지 Green인지 파악합니다.

Bash

```
CURRENT_UPSTREAM=$(docker exec $NGINX_CONTAINER grep -o 'playlist-backend-[a-z]*' /etc/nginx/nginx.conf | head -1)
```

- `docker exec playlist-nginx`: Nginx 컨테이너 내부에서 명령을 실행합니다.
    
- `grep -o 'playlist-backend-[a-z]*'`: 정규식에 매칭되는 문자열(`playlist-backend-blue` 등)만 추출합니다.
    
- `/etc/nginx/nginx.conf`: 대상 설정 파일입니다.
    
- `head -1`: 여러 줄이 나올 경우 첫 번째 줄만 가져옵니다.
    

이를 통해 `CURRENT_UPSTREAM="playlist-backend-blue"` 값을 얻고, 이후 조건문을 통해 `ACTIVE=blue`, `NEXT=green`, `NEXT_PORT=8082`로 배포 변수를 자동 세팅합니다.

### ② Upstream 교체 및 트래픽 전환 (설정 파일 수정)

헬스체크 통과 후, 실제로 트래픽을 전환하는 구간입니다.

Bash

```
docker exec $NGINX_CONTAINER sed -i \
    "s/server playlist-backend-${ACTIVE}:${ACTIVE_PORT}/server playlist-backend-${NEXT}:${NEXT_PORT}/g" \
    /etc/nginx/nginx.conf
```

- `sed -i "s/찾을것/바꿀것/g"`: 파일 내부의 텍스트를 In-place 방식으로 교체합니다.
    
- 실행 결과 예시: `server playlist-backend-blue:8081` ➔ `server playlist-backend-green:8082`
    

이후 Nginx 리로드를 통해 설정값을 즉각 반영합니다.

Bash

```
docker exec playlist-nginx nginx -s reload
```

> **💡 Point:** `reload` 명령은 프로세스를 재시작하는 것이 아니라 설정 파일만 다시 읽게 하므로 **기존 사용자들의 연결이 끊기지 않습니다.**

## 4. 🚨 트러블 슈팅 및 주의사항

배포 파이프라인 구축 및 운영 중 발생할 수 있는 이슈와 해결책입니다.

### Issue 1. Jenkins 컨테이너에서 헬스체크(curl) 실패 이슈

- **원인:** Jenkins가 컨테이너 환경에서 실행 중이어서, 백엔드 컨테이너가 속한 `app-network`(`172.19.0.x` 대역)로 직접 접근할 수 없는 네트워크 격리 문제가 발생했습니다.
    
- **해결:** 백엔드와 동일한 네트워크에 있는 Nginx 컨테이너를 경유하여 헬스체크를 수행하도록 수정했습니다. (`docker exec nginx curl ...`)
    
- **추가 조치:** 기본 `nginx:alpine` 이미지에는 `curl`이 포함되어 있지 않아 위 명령어가 실패합니다. 따라서 **Nginx Dockerfile에 `curl` 설치 구문을 반드시 추가**하여 이미지를 빌드해야 합니다.
    

### Issue 2. Nginx 재시작 시 Upstream 초기화

- **상황:** Nginx 컨테이너가 재시작되면 Dockerfile에 의해 COPY된 원본 `nginx.conf`(`server playlist-backend-blue:8081;`)로 설정이 덮어씌워집니다.
    
- **해결 및 안전성 보장:** Jenkins 파이프라인(Jenkinsfile)의 실행 순서가 이를 커버합니다.
    
    1. `nginx` 컨테이너 재시작 (blue로 초기화됨)
        
    2. `deploy.sh` 실행
        
    3. 스크립트가 "현재 blue"임을 감지하고 자동으로 "green"에 새 버전을 배포
        
    4. Nginx의 타겟을 다시 green으로 교체
        
- 따라서 Nginx 컨테이너가 재시작되어도 파이프라인의 순서가 보장되어 있으므로 **정상적으로 동작**합니다. Nginx.conf 원본 파일의 주석 라인은 배포 스크립트의 `sed` 명령어에 영향을 주지 않으므로 그대로 두어도 무방합니다.
