# Research: 무중단 배포 (Zero-Downtime Blue/Green Deployment)

  
## 1. 현재 배포 구조 분석

### 1.1 현재 Jenkinsfile 배포 단계 (`Deploy to Prod` stage)

```groovy

sh "docker compose -f docker-compose.prod.yml pull backend-blue backend-green nginx"

sh "docker compose -f docker-compose.prod.yml up -d --force-recreate backend-blue backend-green nginx"

```

**문제점**: `--force-recreate`로 blue, green, nginx를 **동시에 내렸다 올림**.  
→ backend-blue 컨테이너가 재시작되는 수 초~수십 초 동안 **서비스 완전 중단(Downtime) 발생**.
→ Blue/Green 인프라는 이미 갖춰져 있지만, **Jenkins 스크립트가 이를 활용하지 않고 있음**.

  
---

### 1.2 현재 인프라 현황 (이미 갖춰진 것들)


| 구성 요소                     | 현재 상태                             | 비고               |
| ------------------------- | --------------------------------- | ---------------- |
| `backend-blue` (포트 8081)  | ✅ 운영 중 (restart: always)          | 현재 트래픽 수신 중      |
| `backend-green` (포트 8082) | ✅ 컨테이너 정의됨 (restart: on-failure)  | 대기 상태            |
| `nginx upstream`          | ✅ `playlist-backend-blue:8081` 고정 | green 주석 처리됨     |
| `nginx -s reload`         | ✅ Nginx가 지원하는 무중단 설정 리로드          | 기존 커넥션 유지됨       |
| `Spring Actuator /health` | ✅ Actuator 의존성 존재                 | 헬스체크 엔드포인트 활용 가능 |

**결론**: 인프라는 이미 Blue/Green을 지원하도록 설계되어 있다. **Jenkinsfile의 배포 스크립트만 교체**하면 된다.

  
---

### 1.3 nginx.conf 현재 upstream 구조

```nginx

upstream backend {

    server playlist-backend-blue:8081;

    # server playlist-backend-green:8082;  # Green 전환 시 주석 해제

}

```

현재는 주석을 수동으로 바꿔서 `nginx -s reload` 하는 **수동 전환** 구조.  
→ 이를 **자동화 스크립트**로 대체해야 함.

## 2. 무중단 Blue/Green 배포 원리

```

[배포 전]

트래픽 →  Nginx  →  backend-blue (v1, 운영 중)

                    backend-green (미실행 또는 구버전)

  

[배포 단계]

1. 새 이미지 Pull

2. backend-green (v2) 컨테이너 시작

3. green 헬스체크 통과 대기 (curl /actuator/health)

4. nginx upstream을 green으로 교체 → nginx -s reload

   (기존 blue 연결은 유지, 새 요청만 green으로)

5. backend-blue 컨테이너 중지

  

[배포 후]

트래픽 →  Nginx  →  backend-green (v2, 운영 중)

                    backend-blue (중지됨, 다음 배포 대기)

```

## 3. 핵심 구현 방법 - 배포 스크립트

Jenkinsfile의 `Deploy to Prod` stage를 하나의 쉘 스크립트로 대체.  

Jenkins가 EC2 동일 서버에서 실행 중이므로(`/workspace/S14P21B206/...` 경로 직접 접근 가능) **SSH 없이 직접 shell 실행** 가능.

### 스크립트 동작 흐름

```bash
# 1. 현재 활성 컬러 감지
#    nginx.conf를 읽어서 blue/green 중 어떤 게 현재 upstream인지 판단

# 2. 비활성 컬러(다음) 결정
#    active=blue → next=green (8082)
#    active=green → next=blue (8081)

# 3. 새 이미지 pull (next 컨테이너용)

# 4. next 컨테이너 --force-recreate로 시작

# 5. 헬스체크 루프
#    curl http://localhost:{next_port}/actuator/health
#    최대 60초 대기, 실패 시 rollback

# 6. nginx.conf upstream을 next로 교체
#    sed 명령어로 in-place 수정

# 7. docker exec playlist-nginx nginx -s reload
#    (Nginx 무중단 설정 반영 - 기존 커넥션 유지)

# 8. active 컨테이너(구버전) 중지
```

## 5. 주의사항 및 고려 포인트

### 5.1 프론트엔드(Nginx)는 무중단 처리가 필요한가?

**결론: 프론트는 Blue/Green 무중단 처리 불필요.**


Nginx 컨테이너는 프론트 정적 파일 서빙 + 리버스 프록시 두 역할을 동시에 함.  
프론트 코드가 변경될 때만 Nginx 컨테이너를 새 이미지로 재시작하면 되는데,  
Nginx 재시작 시간은 수 초 이내로 매우 짧아 실질적인 서비스 영향이 거의 없음.  

반면 Spring Boot 백엔드는 JVM 기동 시간이 수십 초이므로 무중단 처리가 반드시 필요.
→ **Nginx(프론트)는 기존처럼 `--force-recreate` 재시작 유지, 백엔드만 Blue/Green 전환 적용.**

  
### 5.2 Blue/Green 컨테이너의 버전 관계
Blue와 Green은 **항상 동일한 버전이 아님**. 교대로 최신/이전 버전이 됨.

```
[1차 배포]  Blue(v2, 운영 중) ← 트래픽     Green(v1, 중지)
[2차 배포]  Blue(v2, 중지)               Green(v3, 운영 중) ← 트래픽
[3차 배포]  Blue(v4, 운영 중) ← 트래픽     Green(v3, 중지)
```

**스크립트의 핵심 역할**: master 병합 시 Jenkins가 새 이미지를 Docker Hub에 올리면,  
스크립트가 현재 활성 컨테이너를 감지하고 **비활성 컨테이너에만** 새 이미지를 적용한 뒤 트래픽을 전환.  
→ 현재 Jenkinsfile처럼 blue를 항상 고정으로 재시작하는 방식 제거.


### 5.3 스테이징 테스트 활용 (Blue/Green 추가 장점)

비활성 컨테이너(예: Green)를 **스테이징 환경으로 활용** 가능.

```
현재 Blue(v2)가 운영 중

→ Green에만 v3 배포 (트래픽 전환 없이)

→ EC2에서 직접 Green 포트(8082)로 접근해서 테스트

→ 문제 없으면 Nginx upstream 전환 → Green이 운영

→ 문제 있으면 Green만 롤백 (Blue는 여전히 운영 중이므로 서비스 무중단)
```

이것이 Blue/Green의 핵심 장점 중 하나. **운영 중단 없이 신버전 검증 가능.**

### 5.4 nginx.conf upstream 전환 방식

`nginx.conf`는 nginx **Docker 이미지 안에 COPY**되어 있음 (`nginx/Dockerfile` 참고).  
→ 런타임에 컨테이너 내부의 `/etc/nginx/nginx.conf`를 `sed`로 수정 후 reload.  
→ **방식 A (docker exec + sed)** 채택: docker-compose.prod.yml 수정 없이 현 구조 최소 변경.  

단, nginx 컨테이너가 재시작되면 이미지 내 원본 conf로 돌아가므로,  

배포 스크립트 앞부분에서 현재 활성 컬러를 conf 파일 기준으로 감지하는 로직이 중요.

### 5.5 헬스체크 엔드포인트
`/actuator/health`는 현재 SecurityConfig에서 `permitAll()`로 열려있어 인증 없이 접근 가능. ✅  
단, Nginx에서 `actuator` location에 `allow 172.16.0.0/12; deny all;` 제한이 있음.  

→ 헬스체크 curl은 **Nginx를 거치지 않고** 컨테이너 포트(8081/8082)에 직접 접근해야 함.

### 5.6 첫 배포 시 green이 꺼져있는 상황
현재 green은 `restart: on-failure`로 평소에는 꺼져 있음.  
스크립트가 첫 실행 시에도 정상 동작하도록 처리 필요.


---

## 6. 결론

- **"Jenkinsfile에 무중단 배포 스크립트만 추가하면 된다"** → 사실상 맞음.
- 정확히는 Jenkinsfile + 별도 `infra/scripts/deploy.sh` 스크립트 파일 추가 조합.
- `docker-compose.prod.yml`은 **건드릴 필요 없음** (이미 준비됨).
- **프론트(Nginx)는 무중단 처리 불필요** - 재시작 시간이 매우 짧고 Blue/Green 구조 불필요.
- **백엔드만 Blue/Green 전환 자동화** - nginx upstream을 `sed`로 교체 후 `nginx -s reload`.
- 비활성 컨테이너를 스테이징 환경으로 활용 가능 (운영 영향 없이 신버전 검증).

## Step 1: `infra/scripts/deploy.sh` 신규 생성

Blue/Green 전환 로직을 담당하는 핵심 스크립트. Jenkins에서 호출됨.


**구현 내용:**
```

1-1. nginx 컨테이너 내부의 nginx.conf를 읽어 현재 활성 컬러 감지
     → "playlist-backend-blue" 문자열 있으면 active=blue, 없으면 active=green

1-2. next 컬러 및 포트 결정
     → active=blue  : next=green, next_port=8082, next_container=playlist-backend-green
     → active=green : next=blue,  next_port=8081, next_container=playlist-backend-blue


1-3. Docker Hub에서 최신 이미지 pull

1-4. next 컨테이너 --force-recreate 로 시작
     (docker compose -f docker-compose.prod.yml up -d --force-recreate {next})
 

1-5. 헬스체크 루프 (최대 60초, 3초 간격)
     → curl -sf http://localhost:{next_port}/actuator/health
     → 통과 시 다음 단계 진행
     → 타임아웃 시 next 컨테이너 중지 후 스크립트 exit 1 (롤백)

1-6. nginx.conf upstream 교체
     → docker exec playlist-nginx sed -i 명령으로
       "playlist-backend-{active}" → "playlist-backend-{next}" 치환

1-7. nginx 무중단 설정 리로드
     → docker exec playlist-nginx nginx -s reload


1-8. 구버전(active) 컨테이너 중지
     → docker compose -f docker-compose.prod.yml stop {active}
```

## Step 2: `infra/Jenkinsfile` 수정

`Deploy to Prod` stage의 기존 배포 방식을 `deploy.sh` 호출로 교체.

**현재 코드 (제거 대상):**
```groovy
sh "docker compose -f docker-compose.prod.yml pull backend-blue backend-green nginx"

sh "docker compose -f docker-compose.prod.yml up -d --force-recreate backend-blue backend-green nginx"
```

**교체 후:**
```groovy
// 1. 프론트(Nginx) 이미지 pull + 재시작 (기존 방식 유지, 다운타임 감수)
sh "docker compose -f docker-compose.prod.yml pull nginx"

sh "docker compose -f docker-compose.prod.yml up -d --force-recreate nginx"

  

// 2. 백엔드 Blue/Green 무중단 배포 (스크립트 위임)
sh "chmod +x scripts/deploy.sh"

sh "bash scripts/deploy.sh"
```
