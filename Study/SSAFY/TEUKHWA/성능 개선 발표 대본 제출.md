
[성능 개선]
저희는 실제 유저 트래픽으로 서버를 터트려보겠다는 큰 포부를 가졌지만, 그만큼의 유저를 모으진 못했습니다.
그래서 가상 유저를 만들어 직접 부하 테스트를 진행했습니다.

현재까지의 테스트 결과, 개발 서버 기준으로 동시 접속자 970명 정도는 에러 없이 거뜬히 버텨냈습니다.
겉보기엔 아주 안정적이었죠. 하지만, 여기에는 치명적인 함정이 있었습니다.

(화면 전환 - p99 2.8초 지표 띄우기)
![[Pasted image 20260327005418.png]]

평균 속도는 빨랐지만, 운이 나쁜 하위 1%의 유저들은 화면이 뜰 때까지 무려 2.8초나 기다려야 했습니다.
사용자가 지루함을 느끼고 이탈한다는 '1초의 법칙'을 완전히 위반한 심각한 수치였죠.

(화면 전환 - 단일 DB 병목 구조 설명 화면)

원인은 데이터베이스 병목에 있었습니다.

if (BTS 얘기를 넣는다면) {
	BTS가 저희 서비스에 참여했다는 가정을 해봅시다.
	스토리를 올린지 1분도채 되지 않아서 전세계에서 트래픽이 쏠리게 됩니다.
	BTS의 플리에 노래를 추가하기 위해 노래를 검색하고, 추천하고, 또 누군가는 조회를 합니다.
} else {
	저희 서비스는 설계상 곡을 추가하는 작업과 남의 플리를 구경하는 작업이 쉴 새 없이 일어납니다.
}

그런데 이 두 작업이 하나의 DB를 같이 쓰다 보니, 트래픽이 몰리면 구조적 경합이 발생했습니다.

즉, 누군가 곡을 추가할 때 발생하는 지연이 단순히 구경만 하려는 유저들의 발목까지 잡아버린 겁니다.

// 이건 서버 스펙을 아무리 올려도 결국 DB 앞에서 기다려야 하는 건 똑같기 때문에 해결되지 않는 문제였습니다.

그래서 저희는 시스템 구조 자체를 뜯어고쳤습니다.

첫째, '곡 추가' 작업은 카프카에 던져놓고, 유저에게는 즉시 "201 추가 요청 완료" 응답을 주도록 처리했습니다.
둘째, '읽기 전용 DB'를 따로 분리했습니다. 이제 곡을 추가하는 작업이 플리를 조회하는 작업에 전혀 영향을 주지 않게 된 것이죠.
