
여러 시행착오를 거쳐서 제대로 된 테스트 결과를 만났는데요,

우선 테스트의 전제 사항을 말씀드리면, 운영 서버와 개발 서버의 스펙 차이가 대략 2배입니다. 그런데 스펙 차이가 2배라고 성능도 2배가 나오진 않습니다. 암달의 법칙에 따르면 DB 커넥션 대기처럼 순차 처리될 수밖에 없는 부분이 있기 때문에, 실제 향상은 약 1.4배에 그칩니다.

![[Pasted image 20260327005513.png]]

원인은 다음과 같습니다. 곡 추가 같은 쓰기 작업이 DB 커넥션을 길게 또는 동시에 많이 점유하면서, 단순한 플레이리스트 조회마저 커넥션 획득 대기열에 빠져버립니다. 하나의 DB를 읽기와 쓰기가 나눠 쓰기 때문에 발생하는 구조적 경합입니다.

서버를 스케일업해도 제일 앞단에서 요청을 받는 톰캣 스레드가 DB 응답을 기다리며 멈춰 있는 한, 이 문제는 반복됩니다. DB를 늘려도 애플리케이션이 동기 블로킹 방식으로 짜여 있으면 스레드가 응답을 기다리는 동안 다른 요청을 처리하지 못합니다.

따라서 두 가지 개선을 적용했습니다.

첫째, **Kafka 기반 비동기 아키텍처** 도입. 쓰기 요청은 Kafka 큐에 넣고 즉시 응답하여, 쓰기가 읽기를 방해하지 않도록 합니다.

둘째, **읽기/쓰기 DB 분리(CQRS)**. 현재는 하나의 DB에 읽기와 쓰기가 몰려 Lock 경합이 발생합니다. 읽기 전용 복제본(Read Replica)을 분리하면, 쓰기 트랜잭션의 Row Lock이 읽기 쿼리에 영향을 주지 않게 됩니다.

- **쓰기 지연(Write Latency):** 62ms $\rightarrow$ 42ms (**20ms 단축, 약 32.2% 성능 향상**)

## 📌 추신: 질문 대비 — 핵심 개념 & 공식 정리

### 1. Little's Law (리틀의 법칙)
```
L = λ × W

L = 시스템 내 평균 고객 수 (동시접속자)
λ = 초당 도착률 (TPS)
W = 평균 체류 시간 (응답 시간 + Think Time)
```
- **역산**: TPS = 동시접속자 ÷ (응답 시간 + Think Time)
- **예시**: 89 TPS = 1000명 ÷ (0.033초 + 11초)
- **질문 대비**: "Think Time 11초는 어디서 나왔냐?" → 테스트에서 `sleep(10 + random*10)` = 평균 15초지만, 실제 음악 앱 기준 7~15초 랜덤으로 설정. 평균 약 11초.

### 2. Amdahl's Law (암달의 법칙)
```
Speedup = 1 / ((1 - P) + P/S)

P = 병렬화 가능 비율 (CPU 바운드 작업)
S = 스펙 향상 배수
```
- **우리 경우**: DB 커넥션 대기 등 **순차 처리 부분이 약 40%** → `P = 0.6, S = 2`
- `Speedup = 1 / (0.4 + 0.6/2) = 1 / 0.7 ≈ 1.43배`
- **질문 대비**: "왜 1.4배냐?" → DB 커넥션 풀(10개)이 고정이고, 동기식 블로킹이라 CPU를 아무리 올려도 DB 대기 시간은 줄어들지 않음

### 3. Kingman's Formula (킹맨의 공식) — p99가 튀는 이유
```
Wq ≈ (ρ / (1-ρ)) × (Ca² + Cs²)/2 × Ts

ρ = 서버 가동률 (0~1)
```
- **핵심**: 가동률(ρ)이 0.8을 넘으면 대기 시간이 **기하급수적으로** 증가
- 가동률 70% → 대기시간 ×2.3
- 가동률 90% → 대기시간 ×9
- **질문 대비**: "왜 p95는 62ms인데 p99만 2.8초냐?" → 가동률이 높아질 때 운 나쁘게 커넥션 경합에 걸린 1%가 극단적으로 오래 기다리기 때문

### 4. 동시접속자 → DAU 환산
```
DAU = 동시접속자 ÷ 동시접속률
```
- 음악 앱 피크 시간대 동시접속률: **5~10%**
- 970명 ÷ 0.10 = **9,700명** (보수적)
- 970명 ÷ 0.05 = **19,400명** (일반적)
- **질문 대비**: "동시접속률 근거?" → Spotify, 멜론 등 음악 스트리밍 서비스의 피크 시간대(저녁 8~10시) 기준 업계 평균

### 5. CQRS / DB 분리 근거
- **Row Lock 경합**: INSERT/UPDATE 시 MySQL InnoDB가 Row Lock을 걸면, 같은 테이블을 SELECT하는 읽기 쿼리도 Lock 해제를 기다림
- **Read Replica**: 쓰기는 Primary DB에만, 읽기는 Replica에서 처리 → Lock 경합 원천 차단
- **질문 대비**: "결국 일관성(Consistency)은?" → 음악 앱에서 곡 추가 후 0.5초 뒤에 목록에 반영되는 건 허용 가능한 수준 (Eventual Consistency)

### 6. Kafka 도입 근거
- **현재**: `POST /track` → Tomcat 스레드 → DB INSERT (스레드 블로킹 38ms~2.6s)
- **개선**: `POST /track` → Kafka produce (5ms) → 즉시 202 응답 → Consumer가 별도로 DB INSERT
- **질문 대비**: "Kafka가 죽으면?" → Kafka는 디스크 기반 로그라 메시지 유실 없음. Consumer가 재시작하면 밀린 메시지를 순서대로 처리

### 7. 0.1초 / 1초 / 10초 규칙 (Jakob Nielsen)
- **0.1초**: 즉각적 반응, 유저가 지연 인지 못함
- **1.0초**: 한계선, "좀 느리다" 인지 시작
- **10초**: 유저 이탈, 페이지 떠남
- **우리 p99 = 2.8초 → 1초 규칙 위반**

### 🌊 1. 버퍼링(Buffering)과 `sendfile on`
- **기존 방식 (Slow)**: Nginx가 파일을 읽을 때 `Disk -> Kernel Space -> User Space(Nginx) -> Socket Buffer -> Network`라는 복잡한 복사 과정을 거칩니다. 이때 Nginx 메모리에 데이터가 머무는 게 **'버퍼링'**입니다. 
- **`sendfile on` (Fast)**: 복사 과정 다 생략하고 **`Disk -> Kernel Space -> Network`**로 다이렉트로 쏴버립니다. 이걸 핵심 용어로 **'Zero-Copy'**라고 합니다. 
- **효과**: CPU 사용량이 획기적으로 줄고, 파일 전송 속도가 비약적으로 향상됩니다.

### ⚡ 2. `tcp_nodelay on`과 `tcp_nopush on` (병목 해결의 핵심)
- **Nagle 알고리즘 (기본값)**: 네트워크 효율을 위해 데이터가 어느 정도 모일 때까지 기다렸다가 한꺼번에 보냅니다. (이게 3초 지연의 주범!)
- **`tcp_nodelay on`**: 데이터가 모이길 기다리지 않고 **단 1바이트라도 생기면 즉시 전송**합니다.
- **`tcp_nopush on`**: (sendfile과 함께 사용 시) 패킷 헤더를 합쳐서 전송 효율을 극대화합니다.
- **결합 시너지**: "작은 데이터는 즉시 쏘고, 큰 데이터는 가장 효율적인 묶음으로 쏜다"는 전략입니다.

### 🔄 3. `keepalive_requests 1000` (얼마나 유지하나?)
- **Keepalive란?**: 한 번 맺은 TCP 연결(3-way handshake)을 끊지 않고 재사용하는 것입니다. 
- **수치 (100 vs 1000)**: 
  - 기본값 100은 한 연결당 요청 100개까지만 허용하고 끊습니다. 
  - 1,000 VU 테스트에서 유저 1명이 수백 번의 요청을 보낼 때, 100개마다 연결을 새로 맺으면 **CPU가 '연결 맺기/끊기'에만 자원을 다 소모**합니다. 
- **효과**: 연결 유지 횟수를 1,000회로 늘려, 부하 테스트 내내 **연결 노이즈 없이 순수하게 비즈니스 로직(카프카)만 처리**하게 만든 것입니다.

### 💡 왜 3초 이상의 프리징이 해결되었나?

이전에는 Nginx가 1,000명의 요청을 받으면서 **"잠깐, 데이터 좀 더 모을 때까지 기다려(Nagle)"** + **"연결 개수 꽉 찼으니 좀 기다려(Keepalive 100)"** 상태에 빠졌던 것입니다. 

이게 겹치면 요청들이 Nginx 큐에 줄줄이 비엔나처럼 쌓이게 되고, 맨 뒤의 유저는 영문도 모른 채 **3초 이상의 대기**를 타게 됩니다. 

우리는 이번 튜닝으로:
1. **입구(Keepalive)**를 넓게 열어두고,
2. **복사 과정(Zero-Copy)**을 생략했으며,
3. **지연 전송(Nagle)**을 꺼버림으로써 **"물 흐르듯이"** 데이터를 통과시킨 것입니다.

**요약: 고속도로 톨게이트를 없애고(sendfile), 신호를 전부 파란불로 바꾸고(tcp_nodelay), 차량 제한을 대폭 늘린 것(keepalive)과 같은 시너지입니다!
