
프로메테우스 + 그라파나 -> 성능 추적

PostgreSQL (+ pgvector) = 오디오 벡터 데이터로 추천 계산
RDBMS - MySQL = 유저 정보, 플레이리스트 메타데이터, 코멘트 등

DB 서버가 2개가 되면 동기화 문제가 생길 수 있음.

## Kafka를 이용한 실시간 동기화
사용자가 곡을 추가하면 서버에서 메시지를 던지고(Producer) Kafka가 그 메시지를 큐에 넣어서 보관(Broker) 그걸 실시간으로 리스닝하는 컨슈머를 통해 DB에 .저장
비동기적으로 수행되기 때문에 대용량 트래픽도 버틸 수 있고 트랜잭션이 깨지더라도 이어서 보내주는 기능을 포함하고 있기 때문에 데이터 유실률이 0에 가까움.

## 배치를 통한 동기화
오후 시간대에 모인 음원 데이터를 새벽에 한 번에 집어넣기.
- 새벽에 접근하는 사용자들을 고려하면 현실적으로 이상적이지 못함.


# 선택지

> 1. 단일 DB 서버로 1차 배포 후 쿼리문으로 터지거나 부하를 많이 받고난 뒤 스케일 아웃
> 2. 다중 DB 서버로 처음부터 개발


성능 개선을 위해 또는 오버 엔지니어링을 방지하기 위해서 단일 서버로 개발하고 향후 Kafka 도입 예정.




- **Nginx**: 외부 HTTP/HTTPS 요청을 수신하여 활성화된 내부 백엔드 컨테이너(8080/8081)로 트래픽을 포워딩하는 L7 리버스 프록시 및 로드 밸런서.
    
- **Prometheus**: 설정된 주기(Pull 방식)마다 Spring Boot Actuator 및 시스템 메트릭을 수집하여 시계열 데이터베이스(TSDB)에 저장하는 모니터링 시스템.
    
- **Grafana**: Prometheus에 적재된 데이터를 PromQL로 질의하여 시스템 리소스(커넥션 풀, 힙 메모리, 쿼리 지연) 상태를 시각화하는 대시보드 툴.
    
- **무중단 배포 (Blue/Green)**: 신규 버전 컨테이너의 Health Check 통과 시 Nginx의 upstream 지시어를 동적으로 리로드(reload)하여 다운타임 없이 트래픽 경로를 전환하는 배포 아키텍처.
    
- **Spring Boot**: REST API 요청을 처리하고, 비동기 스레드 풀을 활용한 외부 API 통신 및 JPA를 통한 영속성 관리를 수행하는 메인 WAS.
    
- **MySQL**: 트랜잭션(ACID) 및 외래키 제약조건이 필수적인 관계형 데이터(사용자, 플레이리스트 메타데이터, 코멘트)를 영구 저장하는 메인 RDBMS.
    
- **PostgreSQL (pgvector)**: 100만 건 이상의 오디오 피처 데이터를 고차원 벡터로 인덱싱하고, 코사인 유사도(Cosine Similarity) 연산을 수행하는 추천 전용 벡터 데이터베이스.
    
- **Redis**: 높은 I/O 성능을 활용한 외부 API 응답 캐싱 및 인스턴스 간 동시성 제어(분산 락)를 위해 사용하는 인메모리 데이터 스토어.
    
- **Docker 환경 분리**: 컨테이너 오케스트레이션 구성을 Local, Prod, CI/CD 용도로 분리하여 환경의 멱등성을 보장하고 네트워크 및 리소스를 격리하는 인프라 전략.
    
- **Jenkins**: Webhook 트리거로 소스를 빌드하고, DooD 방식으로 도커 이미지를 생성·푸시한 뒤 배포 스크립트를 원격 실행하는 CI/CD 파이프라인 서버.
    

`docker-compose-prod.yml` - 개인 EC2로 체크해볼 거거
```yml
version: '3.8'

services:
  # 1. 리버스 프록시 및 로드 밸런서
  nginx:
    image: nginx:alpine
    container_name: playlist-nginx
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf
    networks:
      - app-network
    restart: always

  # 2. 메인 애플리케이션 (Blue/Green 무중단 배포 대기)
  backend-blue:
    image: ${DOCKER_USERNAME}/playlist-backend:latest
    container_name: playlist-backend-blue
    environment:
      - SPRING_PROFILES_ACTIVE=prod
      - SERVER_PORT=8080
      - MYSQL_URL=jdbc:mysql://mysql:3306/${MYSQL_DB}
      - POSTGRES_URL=jdbc:postgresql://postgres:5432/${POSTGRES_DB}
      - REDIS_HOST=redis
    networks:
      - app-network
    deploy:
      resources:
        limits:
          memory: 400M # 컨테이너당 메모리 하드 리미트
    restart: always

  backend-green:
    image: ${DOCKER_USERNAME}/playlist-backend:latest
    container_name: playlist-backend-green
    environment:
      - SPRING_PROFILES_ACTIVE=prod
      - SERVER_PORT=8081
      - MYSQL_URL=jdbc:mysql://mysql:3306/${MYSQL_DB}
      - POSTGRES_URL=jdbc:postgresql://postgres:5432/${POSTGRES_DB}
      - REDIS_HOST=redis
    networks:
      - app-network
    deploy:
      resources:
        limits:
          memory: 400M
    restart: on-failure # 기본적으로 종료 상태 유지, 배포 스크립트가 기동

  # 3. 트랜잭션 데이터베이스
  mysql:
    image: mysql:8.0
    container_name: playlist-mysql
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_PASSWORD}
      MYSQL_DATABASE: ${MYSQL_DB}
    volumes:
      - mysql_prod_data:/var/lib/mysql
    command: --max_connections=200
    networks:
      - app-network
    deploy:
      resources:
        limits:
          memory: 300M
    restart: always

  # 4. 벡터 데이터베이스 (AI 추천)
  postgres:
    image: pgvector/pgvector:pg16
    container_name: playlist-postgres
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    volumes:
      - postgres_prod_data:/var/lib/postgresql/data
    command: ["postgres", "-c", "max_connections=200"]
    networks:
      - app-network
    deploy:
      resources:
        limits:
          memory: 300M
    restart: always

  # 5. 인메모리 데이터 스토어 (캐싱 및 분산 락)
  redis:
    image: redis:alpine
    container_name: playlist-redis
    command: ["redis-server", "--maxmemory", "128mb", "--maxmemory-policy", "allkeys-lru"]
    networks:
      - app-network
    restart: always

  # 6. 메트릭 수집기 (테스트 목적)
  prometheus:
    image: prom/prometheus
    container_name: playlist-prometheus
    volumes:
      - ./prometheus/prometheus.yml:/etc/prometheus/prometheus.yml
    networks:
      - app-network
    deploy:
      resources:
        limits:
          memory: 256M # OOM Killer 방지를 위한 엄격한 제한
    restart: always

  # 7. 메트릭 시각화 대시보드
  grafana:
    image: grafana/grafana
    container_name: playlist-grafana
    ports:
      - "3000:3000"
    depends_on:
      - prometheus
    networks:
      - app-network
    deploy:
      resources:
        limits:
          memory: 150M
    restart: always

networks:
  app-network:
    driver: bridge

volumes:
  mysql_prod_data:
  postgres_prod_data:
```



# 찐

`Dockerfile`
```yml
# Stage 1: Build 환경 구축 및 의존성 캐싱
FROM eclipse-temurin:17-jdk-alpine AS builder
WORKDIR /app

# 레이어 캐싱을 활용하기 위해 빌드 스크립트 먼저 복사
COPY gradlew .
COPY gradle gradle
COPY build.gradle .
COPY settings.gradle .

# 애플리케이션 소스 코드 변경 시에도 라이브러리 다운로드 시간을 단축 (캐시 히트)
RUN ./gradlew dependencies --no-daemon

# 소스 코드 복사 및 실행 파일(.jar) 빌드
COPY src src
RUN ./gradlew bootJar --no-daemon

# Stage 2: Runtime 환경 구성 (경량화 및 보안)
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app

# 컨테이너 내 프로세스 탈취 시 호스트 OS 보호를 위한 Non-root 유저 생성
RUN addgroup -S spring && adduser -S spring -G spring
USER spring:spring

# Stage 1에서 빌드된 결과물만 복사하여 컨테이너 이미지 크기 최소화
COPY --from=builder /app/build/libs/*.jar app.jar

# JVM 메모리 할당 및 가비지 컬렉터(ZGC) 최적화 옵션 적용 후 컨테이너 실행
ENTRYPOINT ["java", "-Xms512m", "-Xmx512m", "-XX:+UseZGC", "-jar", "app.jar"]
```
