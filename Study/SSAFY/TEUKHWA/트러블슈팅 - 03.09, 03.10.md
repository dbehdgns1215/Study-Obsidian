
# 🚀 인프라/CI/CD 및 트러블슈팅 상세 일지

## 1. 모노레포 환경의 로컬/배포(Prod) 완벽 분리 전략
**[배경]** 모노레포에서 하나의 `master` 브랜치에 CI/CD를 걸어두면, 인프라 담당자가 배포 테스트를 할 때마다 팀원들의 로컬 환경이 꼬이거나 `master` 브랜치가 오염되는 문제가 발생함. 이를 방지하기 위한 3단계 물리적 격리 세팅.

### 1-1. Docker Compose 파일 분리 (가장 중요)
팀원들이 띄우는 로컬 환경과, EC2에서 띄우는 운영 환경의 도커 세팅을 완전히 쪼갠다.
* **`docker-compose.yml` (팀원 로컬 개발용):**
  * Spring Boot나 Nginx는 올리지 않는다.
  * 오직 MySQL, PostgreSQL, Redis 같은 **DB 인프라만** 띄워준다.
  * 팀원들은 이걸로 DB만 띄우고, 백엔드 서버는 인텔리제이에서 재생 버튼을 눌러 로컬(8080)에서 띄우며 개발한다.
* **`docker-compose.prod.yml` (EC2 배포용):**
  * 빌드된 Spring Boot 컨테이너, DB, Nginx, Prometheus 등 전체 스택을 모두 포함한다.
  * CI/CD 파이프라인에서 배포 스크립트를 돌릴 때 `-f` 옵션으로 이 파일만 콕 집어서 실행하게 만든다.

### 1-2. 도커 컨테이너 네이밍 고정 (`container_name`)
* **[이슈]** `docker compose up`은 실행하는 디렉토리(폴더) 이름을 컨테이너 이름의 접두사(Prefix)로 강제 지정함. (예: 로컬에선 `ssafy-mysql-1`, 배포 서버에선 `deploy-mysql-1`). 이로 인해 배포 환경에서 Spring Boot가 DB 컨테이너를 찾지 못해 Connection Refused 에러가 터짐.
* **[해결]** `docker-compose.yml` 내부에 `container_name`을 명시하여 환경에 상관없이 이름을 고정.
```yaml
services:
  mysql:
    image: mysql:8.0
    container_name: real-mysql-db  # 폴더명이 달라도 무조건 이 이름으로 고정
````

### 1-3. Spring Boot 프로필 분리 및 인프라 브랜치 파기

- 환경 변수 충돌 방지를 위해 `application-local.yml` (DB주소: localhost)과 `application-prod.yml` (DB주소: 도커 컨테이너명)로 분리.
    
- 인프라 테스트는 `master`가 아닌 `infra/cicd-setup` 같은 별도 브랜치에서 진행 후, 완벽히 검증됐을 때만 Merge.

## 2. Spring Boot / DB 모니터링 시스템 구축 (Prometheus & Grafana)

**[배경]** 고트래픽 대비 DB 락(Lock) 경합 및 커넥션 풀 상태를 확인하기 위한 중앙 집중형 모니터링 구축.

### 2-1. Spring Boot Actuator 연동

스프링 부트 내부 지표(JVM, HikariCP 커넥션 풀 등)를 프로메테우스가 긁어갈 수(Scrape) 있도록 엔드포인트를 열어줘야 함.

- **1단계: 의존성 추가 (`build.gradle`)**
    

Gradle

```
implementation 'org.springframework.boot:spring-boot-starter-actuator'
implementation 'io.micrometer:micrometer-registry-prometheus'
```

- **2단계: 엔드포인트 개방 (`application.yml`)**
    

YAML

```
management:
  endpoints:
    web:
      exposure:
        include: prometheus
  prometheus:
    metrics:
      export:
        enabled: true
```

### 2-2. 모니터링 연동 장애 트러블슈팅

- **[이슈]** 그라파나 대시보드를 Import 했으나 모든 지표가 `N/A` 또는 `No Data`로 출력됨.
    
- **[분석 과정]**
    
    1. `http://서버IP:8000/actuator/prometheus` 접속 시 `{"detail":"Not Found"}` 에러 발생.
        
    2. 해당 에러 형식은 Spring Boot가 아닌 Python FastAPI 등에서 뱉는 JSON 형태임을 파악.
        
    3. 8000번 포트가 Nginx나 다른 서비스에 물려있음을 확인하고, Spring Boot의 기본 포트인 **8080**으로 접근 포트를 변경하여 해결.

## 3. GitLab CI/CD 파이프라인 최적화

- **[이슈 1] 파이프라인 중복 빌드(Double-build)**
    
    - 원인: GitLab Webhook 트리거 설정에서 `Push events`와 `Merge Request events`가 동시에 체크되어 있어, 한 번의 코드 반영에 젠킨스(또는 GitLab 러너)가 두 번 도는 현상.
        
    - 해결: 트리거 조건을 명확히 분리하여 중복 실행 방지.
        
- **[이슈 2] Docker Build Context 에러**
    
    - 원인: 모노레포 구조 상 최상단 루트와 실제 애플리케이션의 `Dockerfile` 위치가 달라서 COPY 명령어가 작동하지 않음.
        
    - 해결: CI/CD 빌드 스크립트 내에서 `docker build` 명령어의 실행 컨텍스트(경로)를 해당 프로젝트 폴더 구조에 맞게 수정.

## 4. 백엔드(Spring) 및 프론트엔드(React/Vite) 운영 서버 장애 처리

### 4-1. 백엔드 배포 직후 Crash (환경 변수 누락)

- **[증상]** 컨테이너가 뜨자마자 죽음.
    
- **[원인]** 애플리케이션 구동에 필수적인 `GITLAB_BASE_URL`, `JWT_SECRET` 등의 환경 변수가 도커 실행 환경에 주입되지 않음.
    
- **[해결]** 깃허브/깃랩에 하드코딩하지 않고, CI/CD 툴의 보안 변수(Secrets)에 등록한 뒤 도커 실행 시 주입하도록 수정.
    

### 4-2. 프론트엔드 White Screen (빈 화면) 현상

- **[증상]** React/Vite 빌드 후 Nginx로 배포했으나 브라우저에 하얀 화면만 뜸.
    
- **[원인]** Nginx가 정적 파일(JS, CSS)을 내려줄 때 MIME 타입을 지정하지 않아 브라우저가 일반 텍스트로 인식하고 실행을 차단함.
    
- **[해결]** Nginx 설정 파일 (`nginx.conf` 또는 `default.conf`)의 `http` 블록에 아래 코드를 추가하여 해결.
    

```Nginx
include /etc/nginx/mime.types;
```


# 실시간 데이터 전송

보통 실시간 데이터를 가져오는 방법은 3가지가 있습니다.

- **폴링 (Polling)**: 브라우저가 5초마다 "다 됐니?"라고 계속 물어보는 방식입니다. 서버 자원을 낭비하고 반응이 느립니다.
- **웹소켓 (WebSocket)**: 전화 통화처럼 양방향으로 계속 떠드는 방식입니다. 강력하지만 구현이 복잡하고 무겁습니다.
- **SSE (Server-Sent Events)**: **라디오 방송**과 같습니다. 브라우저는 듣기만 하고, 서버는 정보가 생길 때마다 방송을 보냅니다. 양방향 통신까지는 필요 없고, 서버의 소식만 받으면 될 때 **가장 가볍고 효율적**입니다.


### 1. 프로메테우스는 "당기기(Pull)" 방식입니다.

SSE는 서버가 클라이언트에게 "자, 데이터 왔다!" 하고 밀어주는(Push) 방식이죠? 하지만 프로메테우스는 정반대입니다.

- 프로메테우스가 지정된 시간(예: 15초)마다 백엔드에게 전화를 걸어 **"야, 지금 상태 어때? 빨리 말해봐."** 하고 데이터를 **당겨오는(Pull)** 방식입니다.
- 이건 그냥 일반적인 HTTP 통신이지, 연결을 계속 유지하는 SSE가 아닙니다.

### 2. 그라파나는 "새로고침(Polling/Refresh)" 방식입니다.

사용자님이 그라파나 화면을 보고 계실 때, 데이터가 실시간으로 변하는 것처럼 보이죠?

- 사실 그건 실시간이 아니라, 그라파나가 아주 빠르게(예: 5초마다) 프로메테우스한테 **"지금까지 쌓인 데이터 다시 다 보여줘!"** 하고 계속 새로고침을 하고 있는 겁니다.
- 우리가 흔히 말하는 **'폴링(Polling)'** 방식에 가깝습니다.




#### 🦕 0. HTTP/1.0: "매번 차를 빼서 다시 줄 서야 하는 드라이브스루" (1996년)
초창기 웹은 텍스트 몇 줄 띄워주는 게 전부였기 때문에 복잡한 통신 기술이 필요 없었습니다. 그래서 1.0은 아주 단순무식하게 동작했습니다.

치명적인 단점 (단기 연결, Short-lived Connection): 요청을 한 번 보낼 때마다 연결(TCP 통신)을 맺고, 데이터를 받으면 뒤도 안 돌아보고 칼같이 연결을 끊어버립니다.

> 어떤 일이 벌어지나요?

만약 텍스트 1개와 사진 3장이 있는 웹페이지를 띄워야 한다고 가정해 보겠습니다.

- 연결 맺기 -> 텍스트 받기 -> 연결 끊기
- 다시 연결 맺기 -> 사진 1 받기 -> 연결 끊기
- 다시 연결 맺기 -> 사진 2 받기 -> 연결 끊기
- 다시 연결 맺기 -> 사진 3 받기 -> 연결 끊기

비유: 맥도날드 드라이브스루에서 햄버거 세트를 시키는데, 햄버거 하나 받고 차 빼서 동네 한 바퀴 돌고 다시 줄 서서 감자튀김 받고, 또 차 빼서 동네 한 바퀴 돌고 다시 줄 서서 콜라를 받아야 하는 극악의 비효율을 자랑했습니다.

- 놀랍게도 엔진엑스는 기본값이 HTTP/1.0임.

#### 🛒 1. HTTP/1.1: "계산대가 하나뿐인 마트" (현재 가장 흔한 표준)
1997년에 나와서 지금까지도 백엔드 생태계를 지배하고 있는 든든한 국밥 같은 버전입니다.

- 특징: 한 번 연결을 맺으면 끊지 않고 재사용하는 Keep-Alive 기능이 기본입니다. 글자(Text) 기반으로 통신해서 사람이 읽기 편합니다.

- 치명적인 단점 (HOL Blocking): 데이터를 보낼 때 순서대로 1번, 2번, 3번을 보내야 합니다. 만약 1번 데이터(예: 엄청 용량이 큰 이미지) 처리가 오래 걸리면, 뒤에 있는 2번, 3번 데이터는 1번이 끝날 때까지 하염없이 기다려야 합니다. (이걸 Head-of-Line Blocking이라고 부릅니다.)

비유: 마트에 계산대가 하나뿐이라, 내 앞사람이 카트 3개 분량의 물건을 계산하고 있으면 나는 껌 한 통만 사려해도 무조건 기다려야 하는 상황입니다.


#### 🛣️ 2. HTTP/2.0: "하이패스 다차선 고속도로" (웹 속도 혁명)
웹사이트들이 무거워지고(이미지 수십 개, JS 파일 수십 개) HTTP/1.1의 병목 현상이 심해지자, 2015년에 구글의 주도하에 등장한 구원투수입니다.

- 핵심 무기 1 (Multiplexing - 다중화): 이제 순서대로 기다릴 필요가 없습니다! 하나의 연결(파이프) 안에서 여러 개의 데이터를 동시에 쪼개서 막무가내로 섞어 보냅니다. 받는 쪽에서 알아서 조립합니다. 앞사람이 늦게 가든 말든 내 갈 길을 갈 수 있습니다.

- 핵심 무기 2 (바이너리 포맷 & 헤더 압축): 사람이 읽을 수 있는 텍스트 대신 컴퓨터가 처리하기 빠른 0과 1(바이너리)로 통신하고, 매번 중복해서 보내던 무거운 헤더(Header) 정보를 확 압축해 버립니다.

비유: 계산대가 여러 개로 늘어났고, 바코드를 찍는 속도마저 엄청나게 빨라진 최신식 대형 마트입니다.

- 단점: 이 좋은 걸 쓰려면 보안 인증서(HTTPS/SSL) 적용이 사실상 필수입니다. 암호화하고 복호화하는 과정이 들어가니 CPU를 조금 더 씁니다.


#### 🚀 3. HTTP/3.0: "오토바이 퀵서비스" (미래의 표준)
HTTP/2.0도 결국 'TCP'라는 신뢰성 위주의 깐깐한 통신 규약 위에서 돌아가기 때문에, 중간에 패킷이 하나라도 유실되면 전체 통신이 멈칫하는 한계가 있었습니다.

- 특징: 그래서 아예 무겁고 깐깐한 TCP를 버리고, 빠르고 가벼운 **UDP(정확히는 QUIC 프로토콜)**를 기반으로 새로 만들었습니다. 연결 속도도 훨씬 빠르고, 모바일 환경(Wi-Fi에서 LTE로 넘어가는 상황 등)에서도 연결이 끊어지지 않습니다.

비유: 도로의 차선(TCP) 자체를 무시하고, 요리조리 빈틈으로 가장 빠르게 배달을 완료하는 오토바이 퀵서비스입니다. 유튜브나 구글 서비스들에서 이미 적극적으로 쓰고 있습니다.

### 2단계: 도커 컴포즈의 수신 및 가공 (Docker Compose)

이제 도커 컴포즈 파일에서 이 변수들을 어떻게 다루는지 보세요. 사용자님이 주신 코드에 두 가지 방식이 섞여 있습니다.

#### ① `${VARIABLE}` (치환 방식)

- 도커 컴포즈 파일 자체에서 `${MYSQL_HOST}`라고 쓰인 부분은, **도커 컴포즈가 실행되는 순간** 같은 폴더에 있는 .env 파일을 읽어서 그 값을 **글자 그대로 갈아끼웁니다.**
- 예: `MYSQL_HOST=${MYSQL_HOST}` → 컴포즈 실행 시 → `MYSQL_HOST=playlist-mysql`로 변신!

#### ② `env_file:` (파일 통째로 주입)

- **의미**: "이 서비스(컨테이너)가 뜰 때, .env 파일에 적힌 모든 줄을 환경 변수로 다 넣어줘!"
- **차이점**: 위 `${}` 방식은 우리가 필요한 것만 골라서 넣는 방식이라면, `env_file`은 파일 안의 모든 내용을 컨테이너 안에 쏟아붓는 방식입니다. (보통은 하나만 써도 되는데, 혹시 모를 누락을 방지하기 위해 이중으로 해두기도 합니다.)

### 3단계: 최종 목적지 (Spring Boot)

마지막으로 스프링 부트가 이 변수들을 어떻게 인식할까요?

- 도커 컴포즈의 `environment:` 섹션에 적힌 변수들은 컨테이너 내부의 **시스템 환경 변수**가 됩니다.
- 스프링 부트의 `application.properties`는 똑똑하게도 시스템 환경 변수를 자동으로 읽어옵니다.
    
    properties
    
    # application.properties 내부
    
    spring.datasource.url=jdbc:mysql://${MYSQL_HOST}:3306/...
    
- **최종 결과**: 스프링 부트는 자신이 도커 안에서 도는지 모르지만, 환경 변수에 `MYSQL_HOST=playlist-mysql`이 들어와 있으니 그리로 접속하게 됩니다.

---

### 💡 아주 쉽게 요약 (배달 경로)

1. **발주**: 사용자님이 EC2 서버 구석(`secret.env`)에 비밀번호를 직접 적어둠.
2. **택배 집하 (Jenkins)**: 이 파일을 `infra/.env`라는 이름으로 복사해서 도커 컴포즈 옆에 갖다 놓음.
3. **박스 포장 (Docker Compose)**: 작성된 .env를 보고 `${...}` 자리에 값을 채워서 컨테이너라는 박스를 포장함.
4. **배송 완료 (Spring Boot)**: 컨테이너 박스를 열어본 스프링 부트가 "오, 환경 변수들이 다 들어있네!" 하고 사용함.

---

### ⚠️ 주의할 점 (혼동 방지)

- **Environment**: 도커 컴포즈 파일에서 **명시적으로** 변수를 선언할 때 씁니다. (가시성이 좋음)
- **Env_file**: 수십 개의 변수를 일일이 적기 힘들 때 **파일 통째로** 넘길 때 씁니다.
- **Jenkins에서의 `cp`**: Git에 없는 비밀 정보를 **실제 배포 환경에서만** 쓱 끼워 넣는 '신의 한 수'입니다.



# 젠킨스, 도커 중복 빌드

### 최적화된 빌드 흐름

1. 개발자가 코드를 Git에 Push합니다.
    
2. 젠킨스가 웹훅을 감지하고 파이프라인 스크립트를 시작합니다.
    
3. 젠킨스가 Git 저장소에서 최신 소스 코드를 Clone합니다.
    
4. 젠킨스가 쉘 환경에서 `docker build` 명령어를 실행합니다.
    
5. 도커 내부에서 JDK가 포함된 빌드용 베이스 이미지를 컨테이너 메모리에 올립니다.
    
6. 소스 코드 전체를 가져오지 않고, `build.gradle`과 `settings.gradle` 파일만 먼저 도커 내부 작업 디렉토리로 복사합니다.
    
7. 도커 내부에서 프로젝트에 필요한 의존성 라이브러리들을 모두 다운로드합니다. (**이 7번 과정의 결과물이 도커 엔진에 캐시로 영구 저장됩니다.**)
    
8. 라이브러리 캐싱이 완료된 후, 비로소 실제 비즈니스 로직이 담긴 `src` 폴더 전체를 도커 내부로 복사합니다.
    
9. 도커 내부에서 `gradle build` 명령어로 소스 코드를 컴파일하고 `.jar` 파일을 생성합니다.
    
10. 앞서 사용한 무거운 빌드용 이미지는 폐기하고, 만들어진 `.jar` 파일만 JRE가 설치된 가벼운 실행용 베이스 이미지로 복사합니다.
    
11. 완성된 최종 도커 이미지를 젠킨스가 레지스트리에 푸시하거나 서버에서 컨테이너로 실행합니다.
    

### 왜 두 가지 문제가 모두 해결되는가

단순한 비즈니스 로직 코드를 수정하고 재배포할 때, `build.gradle` 파일에 새로운 라이브러리를 추가하지 않았다면 도커는 6번과 7번 과정을 완전히 건너뜁니다.

수백 메가바이트에 달하는 스프링 의존성을 인터넷에서 다시 다운로드하지 않고 기존 캐시를 즉시 재사용합니다. 코드가 변경된 8번 복사 과정과 9번 컴파일 과정만 새로 실행하므로 Option B의 호스트 기반 빌드 속도와 거의 동일한 속도가 나옵니다. 동시에 젠킨스 호스트에는 자바나 그래들을 설치할 필요가 없으므로 환경이 꼬이는 문제도 차단됩니다.
