
## Prod .env 삽질 기록 & 최종 구조 정리

### 1) 무슨 일이었나

- 로컬/레포에는 `plys-backend/.env`, `plys-backend/infra/.env` 가 있고,
- Jenkins 쪽에는 `/var/jenkins_home/secret.env` + Jenkins 워크스페이스 `infra/.env` 가 따로 있었다.
- Spring Boot `application.properties` 에서는 `${ADMIN_EMAIL}`, `${ADMIN_PASSWORD}`, `${KAKAO_CLIENT_ID}` 등을 참조하는데,
  운영 컨테이너 안에서 `env | grep ADMIN`, `env | grep KAKAO` 를 찍어보면 **값이 전혀 없는 상태**였다.

증상:

- prod 백엔드가 부팅 시점에 아래와 같이 터졌다.

  > `Could not resolve placeholder 'ADMIN_EMAIL' in value "${ADMIN_EMAIL}"`

- `.env` 에는 분명히 `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ADMIN_NICKNAME` 가 있었는데도, 컨테이너 안에는 안 들어가 있었다.

---

### 2) 원인 정리

1. **Jenkins가 보는 .env와 내가 수정한 .env가 달랐다**
   - Jenkins `Deploy to Prod` 스테이지에서:
     - 예전에는 `cp /var/jenkins_home/secret.env ./.env` 로 secret.env를 워크스페이스에 복사한 후,
     - `docker compose --env-file .env ...` 을 실행했다.
   - 나는 EC2에서 `/home/ubuntu/workspace/S14P21B206/plys-backend/infra/.env` 만 수정하고 있었고,
     Jenkins가 실제로 쓰는 `/var/jenkins_home/workspace/plys/plys-backend/infra/.env` 는 옛날 값 그대로라,
     신규 `ADMIN_*`, `KAKAO_*` 가 prod에 반영되지 않았다.

2. **컨테이너 재생성을 하지 않으면 env 변경이 반영되지 않는다**
   - `env_file: .env` 는 **컨테이너를 만들 때** `.env` 내용을 복사해 넣는다.
   - 이후 `.env` 파일을 수정해도, 이미 떠 있는 컨테이너에는 자동으로 반영되지 않는다.
   - `docker compose up -d` 가 기존 컨테이너를 재사용하는 한, **env는 계속 옛날값으로 고정**된다.
   - 수동으로 `up -d --force-recreate` 를 때릴 때만 env가 새로 먹었다.

3. **env_file + environment 조합 자체는 문제가 아니었다**
   - 처음에는 `environment:` 때문에 `.env` 의 다른 키(ADMIN/KAKAO)가 “컷” 되는 줄 알았지만,
   - 실제 Docker Compose 동작은:
     - `env_file` 로 모든 키 로드 → `environment` 로 일부 키 override/추가
     - `environment`에 안 적힌 키를 지우지는 않는다.
   - 결론적으로, **구조 탓이 아니라 “어떤 .env로, 언제 만든 컨테이너냐” 문제가 원인이었다.**

### 구버전(V1) vs 신버전(V2) 차이와 주의점

방금 `apt-get install docker-compose`로 설치한 방식은 **구버전(V1)**이 깔리는 함정이 있습니다.

- **구버전 (V1):** `docker-compose` (하이픈 ⭕) - 파이썬 기반의 레거시 방식.
- **신버전 (V2):** `docker compose` (띄어쓰기 ⭕) - Go 언어로 재작성된 최신 표준 플러그인.
    

동훈님의 현재 `Jenkinsfile` 스크립트는 띄어쓰기를 사용하는 **신버전(V2)** 문법으로 작성되어 있습니다. 구버전을 깔아둔 상태로 젠킨스를 돌리면 `docker: 'compose' is not a docker command.` 라면서 파이프라인이 그 자리에서 즉사합니다.

`Jenkinsfile`을 일일이 뜯어고칠 필요 없이, 젠킨스 컨테이너 안에 띄어쓰기가 먹히는 신버전(V2) 플러그인을 꽂아버리는 게 가장 깔끔합니다.

# CORS

---

### 1. SOP (Same-Origin Policy) - 모든 것의 시작

브라우저가 가진 기본 보안 정책. **"다른 출처의 리소스는 건드리지 마라"** 는 규칙.

**Origin(출처) 정의** = `프로토콜 + 도메인 + 포트` 세 개가 전부 같아야 Same-Origin

```
https://j14b206.p.ssafy.io:443   (기준)

https://j14b206.p.ssafy.io       → 같음 (443 기본 포트 생략)
http://j14b206.p.ssafy.io        → 다름 (프로토콜 다름)
https://j14b206.p.ssafy.io:8081  → 다름 (포트 다름)
https://j14b206.other.io         → 다름 (도메인 다름)
```

---

### 2. 왜 SOP가 필요한가

SOP 없으면 이런 공격이 가능:

```
1. 니가 evil.com 에 접속
2. evil.com의 JS가 브라우저 안에서 실행됨
3. 그 JS가 몰래 https://your-bank.com/transfer?to=hacker 를 호출
4. 브라우저에 이미 bank.com 쿠키(로그인 정보)가 있으므로 인증 통과
5. 돈이 빠져나감
```

이게 **CSRF(Cross-Site Request Forgery)** 공격. SOP가 다른 Origin의 JS가 타 도메인에 함부로 요청하지 못하게 막음.

---

### 3. 그런데 왜 CORS가 필요한가

SOP가 너무 엄격해서 **합법적인 크로스 오리진 요청도 전부 막힘**.

```
프론트: http://localhost:5173   (개발 서버)
백엔드: http://localhost:8081   (Spring Boot)

→ 포트 다름 → 다른 Origin → SOP에 의해 차단
→ 근데 이건 개발자가 의도한 정상 요청
```

그래서 등장한 게 CORS. **"서버가 명시적으로 허락한 출처에서의 요청은 통과시켜줄게"** 라는 메커니즘.

---

### 4. CORS 동작 방식 - 두 가지 케이스

**케이스 1: Simple Request (단순 요청)**

GET 이고 커스텀 헤더 없으면 브라우저가 바로 요청 날림. 응답 헤더에 `Access-Control-Allow-Origin` 없거나 맞지 않으면 브라우저가 응답을 JS에 넘겨주지 않음. 요청 자체는 서버에 도달함.

**케이스 2: Preflight Request (사전 요청)**

POST + `Content-Type: application/json` 이거나 커스텀 헤더(`Authorization` 등) 붙으면, 브라우저가 실제 요청 전에 **`OPTIONS` 메서드로 사전 탐색**을 먼저 날림.

```
브라우저 → OPTIONS /api/auth/check-email
           Origin: https://j14b206.p.ssafy.io
           Access-Control-Request-Method: POST
           Access-Control-Request-Headers: Content-Type

서버 응답 → Access-Control-Allow-Origin: https://j14b206.p.ssafy.io  ← 이게 있어야
            Access-Control-Allow-Methods: POST
            Access-Control-Allow-Headers: Content-Type

→ OK면 실제 POST 요청 날림
→ 응답에 해당 헤더 없으면 "Invalid CORS request" 에러, 실제 요청도 안 날림
```

**이번 에러가 정확히 이 케이스.** `POST /api/auth/check-email` 보내기 전에 `OPTIONS` 날렸더니 서버가 `https://j14b206.p.ssafy.io` 를 허용 목록에서 못 찾아서 거부.

---

### 5. Spring Boot가 하는 일

서버는 CORS를 **응답 헤더**로 통제함. Spring Security의 `corsConfigurationSource()`가 하는 일:

```
클라이언트 요청의 Origin 헤더를 읽음
  → 허용 목록에 있으면 응답에 Access-Control-Allow-Origin 헤더 추가
  → 없으면 아무 헤더도 안 붙임
  
브라우저는 응답에 그 헤더가 없으면 "CORS 위반"으로 처리하고 JS에 응답 안 넘겨줌
```

---

### 6. 이번 에러 흐름 정리

```
배포 브라우저
  → OPTIONS https://j14b206.p.ssafy.io/api/auth/check-email
    헤더: Origin: https://j14b206.p.ssafy.io

Nginx (프록시)
  → Spring Boot로 전달

Spring Security CORS 필터
  → 허용 목록: [localhost:3000, localhost:5173]
  → j14b206.p.ssafy.io ? → 없음
  → 응답에 Access-Control-Allow-Origin 헤더 미포함

브라우저
  → Access-Control-Allow-Origin 없네?
  → "Invalid CORS request" 에러
  → 실제 POST 요청도 차단
```

**같은 도메인인데 왜?** 라고 느껴지지만, Nginx가 프록시하는 것은 서버 내부 라우팅이고, **브라우저는 그걸 모름**. 브라우저 입장에서 백엔드 응답도 `j14b206.p.ssafy.io`에서 오는 것처럼 보이는 게 맞는데, Origin 헤더는 요청을 시작한 페이지의 출처를 명시하는 것이라 Spring Boot가 받는 순간 판단해야 함.

**핵심**: CORS는 서버가 판단하는 게 아니라 **브라우저가 강제**하는 보안 정책. 서버는 허용 헤더만 응답에 추가해줄 뿐.
